## 1. 证据分级

为每条拟沉淀规则标记来源：

| 等级 | 含义 | 可否写成稳定规则 |
|---|---|---|
| A 用户确认事实 | 用户明确确认，且没有后续推翻 | 可以 |
| B 工具观察 | 文件、日志、测试或线上读回直接证明 | 可以，注明适用环境 |
| C 多源一致 | 用户确认与工具观察相互印证 | 优先写入 |
| D Agent 推断 | 从上下文推导，但未获确认或缺少直接证据 | 不可以，保留为待确认 |
| E 未知 | 对话缺失、任务压缩后不可恢复或结果相互矛盾 | 不可以 |

“Agent 说成功”“命令退出码为 0”“请求已发出”只能证明局部动作，不能自动证明业务任务完成。

## 2. 理解偏差抽象

用户的不满和纠正是定位理解偏差的证据，不是可以直接复制为 Skill 规则的结论。先建立一条可核对的“纠偏链”：

1. **用户原意**：引用原话或忠实释义，说明用户要求的是内容、方法、叙事逻辑还是输出格式。
2. **错误理解或行为**：指出实际答案、文件或操作中可观察的偏差，不猜测 Agent 的心理过程。
3. **用户纠正**：记录用户明确否定的内容和重新说明的意图。
4. **理解偏差**：说明哪一层要求被错误转换成了哪一层要求。
5. **通用规则**：写成“当出现什么条件时，应如何判断或行动”。
6. **适用边界**：写清哪些明确信号出现时，这条规则不适用。

常见的理解偏差包括：

- 把思考维度或叙事框架机械转换成可见标题、字段或栏目；
- 把方法原则当成必须逐字出现的固定话术；
- 把示例当成唯一模板；
- 把优先级要求理解成只能保留一个方面；
- 把用户纠正后的最终答案直接改写成“通用规则”，但没有解释此前错在哪里。

### 框架含义与输出格式的判断

当用户提出 STAR、金字塔原理、问题—方案—结果等框架时，先判断其作用层：

| 作用层 | 典型含义 | 默认处理 |
|---|---|---|
| 思考维度 | 内容需要覆盖哪些方面 | 在内容中完整体现，不显示框架标签 |
| 叙事逻辑 | 信息应按什么关系和顺序组织 | 用自然语言呈现，不机械分栏 |
| 输出格式 | 用户明确要求标题、字段、表格或模板 | 按指定结构显式输出 |

“分栏、标题、字段、表格、逐项填写、按模板输出”等属于显式格式信号。没有这些信号时，不要仅因用户提到框架名称就创建同名栏目。

示例：

- 原意：按照背景、行动和结果的叙事来写。
- 错误理解：固定输出“背景”“行动”“结果”三个字段。
- 通用规则：用户引用框架但未要求显式格式时，应把框架作为内容或叙事约束隐含应用。
- 适用边界：用户明确要求“三栏展示”或“每项分别填写”时，应保留字段。

### 跨场景检验

通用规则至少通过两个不同任务的替换检验，例如：

- “按金字塔原理写汇报”不等于必须出现“结论、理由、行动”三个标题；
- “按风险评估思路给方案”不等于必须输出固定风险登记表；
- 若用户明确要求“三列对比表”，则必须尊重显式结构。

若规则只能解释本次答案、换一个任务就失效，或必须依赖本次项目事实才能成立，则不进入 Skill 候选。

## 3. 可复用性门禁

候选至少同时满足以下条件：

- 能写出明确的未来触发场景；
- 预计会再次发生，或虽然低频但风险高、流程复杂且重建成本明显；
- 核心方法不依赖当前日期、账号、项目状态或临时页面；
- 能定义输入、输出和可观察的验收标准；
- 包含普通 Agent 不容易稳定重建的步骤、判断、门禁、模板或工具知识；
- 至少有一条 A、B 或 C 级成功证据；
- 能在删除本次项目名称和一次性结果后仍然成立。
- 来源于用户纠正时，能够还原完整纠偏链并通过至少两个不同任务的替换检验。

出现以下任一项时，不创建 Skill：

- 任务仍未完成或最终结果未验收；
- 只有一次性答案，没有可重复的方法；
- 故障根因和恢复路径仍是推测；
- 内容主要是个人偏好、项目状态、人员、日期或资源 ID；
- 无法定义不适用范围或完成标准；
- 无法脱敏；
- 只有泄漏预期答案时测试才能通过；
- 与现有 Skill 高度重叠但无法确认归属或修改权限。
- 只复述最终修改清单，无法说明原意、错误理解和适用边界。

## 4. 抽象边界

使用下列问题确定抽象粒度：

1. 下一次用户会用什么话触发这项能力？
2. 不同任务之间，哪些输入会变化？
3. 哪些步骤必须保持稳定？
4. 哪些判断需要证据或人工审批？
5. 最终输出怎样才算可交付？
6. 哪些失败分支已经被真实验证？
7. 把客户名、项目名和本次答案删除后，方法是否仍然完整？
8. 若合并进现有 Skill，是否更容易被正确触发和维护？
9. 这条规则是在指导未来判断，还是只换一种说法描述本次正确答案？
10. 能否给出两个不同领域的适用例和一个明确反例？

优先沉淀“未来如何再次得到正确结果”，不要沉淀“这次的正确结果”。

## 5. 载体路由

| 内容性质 | 推荐载体 |
|---|---|
| 重复执行的专项工作流 | 新 Skill 或现有用户自有 Skill |
| 与已有 Skill 的目标、触发和输出相同 | 更新现有 Skill |
| 详细领域规则、证据标准、模板和案例 | Skill 的 `references/` |
| 稳定、重复、需要确定性执行的代码 | Skill 的 `scripts/` |
| 最终输出直接复用的模板、图片或字体 | Skill 的 `assets/` |
| 用户偏好、个人习惯、跨项目经验 | Memory；只有用户明确要求才写入 |
| 项目长期规则 | 项目 `AGENTS.md`；先取得相应授权 |
| 项目状态、人员、日期、表或记录 ID | 项目文档，不进通用 Skill |
| 一次性结果、临时故障、未验证推断 | 不沉淀，或仅保留任务复盘 |

## 6. 候选确认卡

最多展示三个候选，推荐项排在第一。

```markdown
候选 1：<动词开头的暂定名称>

- 解决的问题：
- 未来触发示例：
- 预期输入：
- 预期输出：
- 可复用核心：
- 用户原意：<存在纠正证据时必填>
- 错误理解或行为：<只写可观察事实>
- 用户纠正：<用户明确否定和重新解释的内容>
- 通用防错规则：<条件 + 判断或行动>
- 适用边界：<何时不采用该规则>
- 跨场景检验：<两个不同任务的适用例>
- 本次证据：<A/B/C 级证据及出处>
- 将排除：<一次性事实、敏感内容、未验证推断>
- 推荐去向：<新建 / 更新现有 / 其他载体 / 不沉淀>
- 推荐理由：

本轮只确认：是否按候选 1 继续定义 Skill 契约？
```

如果没有合格候选，直接给出“不创建 Skill”的结论、证据缺口和重新评估条件。

没有用户纠正证据的成功流程候选，可以省略“用户原意”至“适用边界”；但仍需完成通用性与跨场景检验。

## 7. Skill 契约确认卡

每轮修正后重发完整契约，避免用户自行拼接散落修改。

```markdown
Skill 契约（待确认）

- name：
- 显示名：
- 一句话目标：
- 正向触发：
- 不应触发：
- 输入：
- 输出：
- 核心流程：
- 权限与人工审批：
- 停止条件：
- 验收标准：
- 新建或更新：
- 关联现有 Skill：
- 最小文件树：
- 研发暂存路径：
- 正式发布路径：
- 回退方式：
- 测试计划：
- 待确认项：
- 推荐默认值及理由：

本轮只确认：是否按这份完整契约进入暂存实现？
```

## 8. 发布确认卡

```markdown
发布审查（待确认）

- 研发稿路径：
- 正式目标路径：
- 新建或更新：
- 文件树或关键差异：
- 结构校验：
- 正向触发测试：
- 负向与边界测试：
- 脚本运行测试：
- 独立前向测试：
- 回归测试：
- 敏感信息与固定事实检查：
- 已知限制：
- 旧版备份路径：
- 回退方法：

本轮只确认：发布、继续修改、保留草稿，还是放弃？
```

只有“发布”允许修改正式目录。“继续修改”返回实现与测试；“保留草稿”和“放弃”均不得触碰正式版本。

## 9. 测试场景设计

至少覆盖：

### 正向触发

- 用户明确要求把一个已完成且有证据的专项任务沉淀成 Skill；
- 用户要求判断应该新建 Skill 还是更新已有 Skill；
- 上级规则明确要求在任务验收后检查 Skill 候选，且用户同意继续。

### 边界场景

- 对话已经压缩，缺少失败过程或验收证据；
- 存在可复用方法，但更适合更新现有 Skill；
- 候选包含客户事实，必须参数化或删除；
- 任务失败，但有一个已验证的故障诊断分支可供更新现有 Skill。
- 用户提到一个框架但没有要求显式字段，候选应区分内容维度与输出格式；
- 用户明确要求分栏、标题或表格，不能以“自然表达”为由取消结构；
- 只有用户最终认可的答案，没有可核对的原始要求、错误表现和纠正过程。

### 负向触发

- 用户只说“任务完成了”；
- 用户只要求普通复盘、保存上下文或记住偏好；
- 用户要求解释一个概念；
- 用户要求把一次未复现、未定位根因的临时故障做成 Skill；
- 用户未确认契约或发布，但 Agent 准备写入正式目录。
- 用户只表达不满或要求重写，没有明确要求沉淀，Skill 不应自动触发。

### 通过标准

- 能拒绝为了沉淀而沉淀；
- 能区分新建、更新、其他载体和不沉淀；
- 能把任务特例从通用方法中剥离；
- 能从用户原意与错误理解的差异中提炼防错规则，而不是复述最终修改清单；
- 能区分框架的思考维度、叙事逻辑和显式输出格式；
- 每条纠偏规则包含适用边界，并通过至少两个不同任务的替换检验；
- 每个确认轮次只处理一个决策；
- 未通过三个门禁时不会产生越权写入；
- 在最少上下文下仍能按证据工作，不依赖测试者知道预期答案。
