# 软件与工具训练轨道

## 适用范围

用于 GUI 软件、CLI 工具、开发平台、数据库工具、部署工具和企业应用，例如 Cherry Studio、Dify、Docker、Git、飞书多维表格、剪映或 IDE。

## 开始前

1. 确认用户最终要独立完成的工作结果，而非“熟悉软件”。
2. 检查操作系统、软件版本、账号状态、现有项目和权限。
3. 版本或界面可能变化时，读取当前官方文档或直接检查实际界面。
4. 使用练习项目、测试账号或可恢复副本；不直接在生产数据上训练。

## 最小真实任务

选择一条端到端工作流，至少包括：

- 创建或打开真实工作对象；
- 完成核心配置或编辑；
- 运行、预览或验证结果；
- 保存、导出、发布到测试环境或重新打开；
- 定位日志、历史记录、状态信息或错误入口；
- 留下可复核的产物。

“找到按钮”不算任务完成。验收最终工作结果及其状态。

## 陪练方式

- 先说明本关结果，让用户在真实界面或终端中操作。
- GUI 指引使用功能名称、页面层级和可观察状态，避免只写坐标或死记点击路径。
- CLI 指引说明命令读取什么、改变什么、正常输出是什么；不要只给复制命令。
- 早期示范后逐步撤掉操作顺序，让用户根据目标自行找到路径。
- 用户提交截图时，检查结果状态、版本和关键字段，不只确认界面相似。

## GUI 控件与界面状态

GUI 指引按“功能身份 → 当前状态 → 执行动作 → 状态变化”组织，不按图标外观猜测：

1. **先确认功能身份**：优先使用界面文字、悬浮提示（tooltip）、具名菜单项或可访问名称。图标的颜色、形状、位置只用于帮助寻找，不能证明控件是什么。
2. **截图优先于记忆**：有用户当前截图时，先读取截图中的软件版本、窗口标题、工具窗口、选中会话和按钮状态。文档或旧版本界面与截图冲突时，以当前界面为准并重新核实功能名。
3. **看不清就停下来核实**：截图不能证明控件身份时，让用户把鼠标悬停到候选控件并返回提示文字；如果仍无法确认，改用当前版本已核实的具名菜单操作。不得让用户“先点一下试试”。
4. **相似动作要明确区分**：运行、调试、继续、暂停、重启、停止，以及保存、应用、发布等容易混淆的动作，分别说明它们改变什么状态和执行后会看到什么。
5. **快捷键有使用前提**：给快捷键前，确认软件版本、当前活动会话和键盘焦点。焦点或会话不明确时，不使用快捷键绕过控件识别。
6. **识别活动会话**：同时存在运行、调试、历史输出或多个服务窗口时，用工具窗口名称、配置名、活动标记、最新日志时间、进程或端口判断当前对象，不能只看内容像不像。
7. **操作后再验收**：点击或按键后，立即核对预期状态变化。若没有发生，停在当前状态排查，不继续发下一串操作。
8. **错指引先恢复**：用户报告图标、页面或状态不一致时，先承认原定位失效，停止新增动作，读取当前截图，只给一个可恢复的步骤；恢复成功后重新建立状态基线。

示例：需要让暂停的调试程序继续运行时，指引必须落到“在当前调试工具窗口里，悬停并确认提示为‘继续程序（Resume Program）’的控件”，不能写成“点绿色三角形”。同一软件中绿色三角形可能代表普通运行，图标也可能随版本、主题和当前状态改变。

## IDE 项目训练

课程或真实工作明确使用 PyCharm、VS Code、IntelliJ IDEA 等 IDE 时，先在该 IDE 中建立可重复的项目运行方式，再继续业务功能：

1. 打开实际项目根目录，确认源码、配置和虚拟环境属于同一个项目；
2. 选择项目解释器或 SDK，验证 IDE 使用的环境与项目依赖一致；
3. 为每个需要反复运行的程序创建具名运行配置，保存入口模块、工作目录、程序参数和环境变量；
4. 持续服务使用独立运行窗口，用户能识别每个窗口运行什么、使用哪个端口、如何停止和重启；
5. 一次性测试也通过运行配置或 IDE 内明确的测试入口执行，除非真实工作流本来就要求 CLI；
6. 至少完成一次断点、变量查看或错误堆栈定位，让用户掌握 IDE 带来的开发能力，不把 IDE 只当成文本编辑器。

终端可以保留为辅助入口，但要说明本次为何必须使用终端。课程和岗位的核心动作在 IDE 中完成时，纯终端输出不能证明用户已掌握该工作流。

## 变式练习

从下列类型中选择一个与目标相关的变化：

- 更换输入文件、数据集或项目；
- 修改一个关键参数或权限；
- 更换导出格式、运行环境或目标位置；
- 从已有对象操作改为从空白对象开始；
- 在不改变最终目标的情况下换一条可行路径。

要求用户先预测变化，再操作并解释实际结果。

## 故障练习

选择安全、可恢复的高频故障，例如：

- 路径、端口、版本或依赖不一致；
- 权限不足、账号状态异常或文件被占用；
- 配置未保存、格式不兼容或参数错误；
- 服务未启动、连接失败或日志出现明确错误；
- GUI 中进入了相似但错误的功能入口。

让用户按“观察现象 → 找证据 → 提出一个原因 → 做区分性检查 → 最小修复 → 重新验证”处理。不要同时给出多个修复方案。

## 独立挑战

使用一个新的输入、项目或约束，要求用户从可识别的起点独立完成同类工作流。只提供：

- 最终目标；
- 不能越过的安全边界；
- 必须提交的成果和证据；
- 完成条件。

完成后，让用户说明关键状态变化、一个可替代路径和一个常见故障的定位方法。
