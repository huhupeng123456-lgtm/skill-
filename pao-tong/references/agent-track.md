# Agent 工程训练轨道

## 适用范围

用于 Prompt、RAG、知识库、MCP、工具调用、Workflow、Agent 编排、Eval、Trace、记忆、Guardrail 和人工审批。

## 能力地图

不要把“掌握 RAG / Agent / MCP”直接当训练任务。按目标选择输入输出子能力，例如：

- 业务需求 → 判断是否适合 RAG、Workflow 或 Agent；
- 文档与查询 → 设计切分、检索和评测；
- 接口文档 → 定义工具输入输出、认证和错误分支；
- 用户请求与工具状态 → 选择路由、回退或人工确认；
- 坏回答、日志或 Trace → 定位失败层；
- 新业务场景 → 搭建并验收最小真实闭环。

场景选择和失败定位属于判别模型；调用、状态和回退属于连接模型；配置、编码、运行与调试属于程序性综合能力。

## 从业务闭环定义任务

内部先确定：业务输入、Agent 判断、工具或数据源、结构化结果、风险阻断或人工确认、Trace 与评测证据。

只生成一段看似合理的回答，不算 Agent 闭环跑通。

## 责任分层

让用户能判断规则放在哪里：

- **Prompt 或 Skill**：目标、模型判断指导、输出契约和工具选择；
- **搜索、API 或数据库**：变化的外部事实和业务数据；
- **程序硬规则**：不能交给模型自由判断的校验、阈值和状态约束；
- **人工确认**：高风险、不可逆、付费、发布或外部沟通；
- **Trace 与 Eval**：记录输入、调用、来源、版本、失败位置和评测结果。

两个方案都可行时，要求用户依据目标、准确性、可解释性、成本、延迟、权限、可逆性和维护责任取舍，不把偏好包装成唯一最佳实践。

## 协议与网络对象层

用户尚未建立调用模型时，按依赖顺序建立：

1. 当前运行中的程序及其文件或模块；
2. 端口是运行中程序的数字入口；
3. 完整地址由主机、端口和路径组成；
4. 协议是通信双方共同遵守的数据与交互规则；
5. 客户端与服务端是一次通信中的发起方和等待方角色；
6. 当前真实请求字段、JSON 序列化和发送过程；
7. HTTP 状态、任务状态、工具结果、界面显示和日志证据的区别。

每次只讲当前操作依赖的最小层级，并用项目真实代码、请求、日志和端点返回验证。多个组件同时出现时重复组件名，不用“它”串联。

状态首次出现时说明：谁把什么标记为什么值、该值表示什么、谁读取、读取后采取什么动作。只有用户需要追查协议字段时才展开字段结构，不提前堆防御性说明。

## Mock 转向真实 Agent 能力

应用 [operation-gates.md](operation-gates.md) 的通用 Mock 门禁，并额外判断：

### 大模型判断被规则替代

规则替代意图识别、查询改写、工具选择或总结时，只能证明规则之后的路由、调用和解析。不能证明自由表达理解、Prompt 有效性、JSON 稳定性、模糊冲突处理、模型质量、延迟或费用。

最小 Mock 后优先转向授权模型 API、本地模型、官方沙箱，或至少形成真实 Prompt、JSON Schema 和代表性 Eval 输入再验证。模型不可用时明确该能力阻塞，只继续外围契约和日志训练。

### 工具或数据源被静态结果替代

静态结果只能证明 Agent 会发起调用并读取返回。真实开发还要补认证、字段映射、超时、重试、幂等、错误码、审计和高风险人工确认中的相关项。没有真实库存、数据库或 API 时，不验收数据准确性和业务成功。

## 最小真实任务

至少包含：

1. 明确业务输入与结构；
2. 可检查的 Agent 判断或路由；
3. 至少一个真实工具、授权数据源或明确 Mock；
4. 结构化输出契约；
5. 一个异常、缺失或边界输入；
6. 一个风险阻断、回退或人工确认点；
7. 可读取的 Trace、日志或 Eval 结果。

动态事实记录来源、查询时间和未知项。Mock 说明替代能力，不声称验证生产效果。

## 训练方式

- 先画清输入、判断、工具、输出和风险边界，再配置或编码。
- 每次搭建或验证一个环节，读取真实返回或 Trace。
- 让用户说明字段、参数、状态和结果怎样变化。
- 可生成脚手架，但核心路由、规则、验收和故障判断由用户完成。
- 多服务项目在目标 IDE 中建立独立具名运行配置，区分持续服务与一次性客户端。
- 首个同构组件完整训练；后续只训练协议、认证、参数、状态、权限、风险或失败处理差异。

## 上层抽象与迁移

完成多个同构组件后，让用户抽出：

- 始终不变的调用契约、责任边界和证据链；
- 每个组件变化的端口、工具名、业务字段、权限或风险；
- 新组件是否仍属于原机制的输入空间；
- 哪个差异要求新训练，哪个只需最小集成验证。

## 变式

一次改变一个重要条件：输入缺失或冲突、工具为空或超时、权限不足、数据过期、模型/Prompt/Schema 变化、风险动作改为人工确认，或切换新业务对象。先预测路由、回退和留痕，再运行核对 Trace。

## 故障

优先选择可观察、可恢复的问题：工具 schema 或字段不匹配、RAG 召回错误、Prompt 与硬规则冲突、输出校验失败、工具未调用或错误重试、人工确认或 Guardrail 未生效。

用户从 Trace 或日志判断失败所在层，提出一个最小修复并完成回归验证。

## 未见独立挑战

给出不同业务输入、工具状态或风险条件，只提供业务目标、可用工具、权限边界、正常/异常/风险场景，以及需要提交的配置、输出、Trace 和 Eval 证据。

完成后要求说明：规则为何放在模型、程序、工具或人工环节；失败如何回退；哪些证据支持可信；哪里不能从练习直接外推到生产。
