# Explain 行为测试

这些案例用于人工或独立前向测试。不要按关键词或固定标题判分；检查 Skill 是否选对了学习任务、材料、诊断和验收方式。未见案例必须与讲解案例表面不同，但保留待测结构。

## Explain 专项案例

### 1. 只知道术语名称

**请求**：我知道 API 中文叫“应用程序接口”，但这几个字对我没有帮助。它在真实软件里到底是什么？

**验证**：识别为“指代已建立、意义和对象层不足”；定位现实调用双方、输入输出和可观察实例；不继续堆词典定义；用一个新软件对象让用户判断是否为当前语境下的 API。

### 2. 会背定义但不会判断

**请求**：我会背“缓存击穿”的定义，但线上一超时就不会判断。不要再背定义。

**验证**：建立观察证据与判断顺序；用正例和相似反例区分；不直接把“超时”确诊为缓存击穿；用未见案例测试判别。

### 3. 同一术语在不同框架中含义不同

**请求**：这门课规定“只有能自主选择工具并根据结果继续行动才叫 Agent”。客服机器人固定调用一次接口，算不算？

**验证**：优先使用课程定义；把通用补充与课程结论分开；指出决定结论的缺失证据；不把某个厂商定义说成唯一真理。

### 4. 内涵与判别模型混淆

**请求**：我知道“Agent 会围绕目标动态决定下一步”，这不就是判断 Agent 的方法了吗？内涵和判别模型到底差在哪？

**验证**：说明“共同属性”与“拿属性检查具体对象的过程”不同；让用户对一个现实系统逐项判断；避免只换一组抽象术语。

### 5. 只有正例导致范围过宽

**请求**：我见过的 Agent 都会调用工具，所以只要大模型调用工具就是 Agent，对吗？

**验证**：识别判别范围过宽；用固定工作流反例和边界例修正充分条件；再用未见案例检查是否仍以“有工具”为唯一标准。

### 6. 把建议当成知识

**请求**：有人说“重要会议必须提前一天发材料”，这到底是知识还是决策？

**验证**：分离可泛化关系与当前行动；说明目标、参与者和时间约束；条件改变时决策应改变，不把“一天”包装成普遍规律。

### 7. 超出知识输入空间

**请求**：数据库连接池耗尽会导致请求超时，所以所有请求超时都可以按连接池耗尽处理，对吗？

**验证**：说清原知识的输入范围、能推出什么和不能排除什么；先判别再处理；用另一类超时作为未见反例。

### 8. 原例理解，新例失败

**请求**：你刚才讲的电商订单状态机我懂，但换成合同审批，我就不知道哪些是状态、哪些是动作了。

**验证**：诊断为迁移或上层抽象不足；比较两个场景，提取“对象、有限状态、触发事件、转换条件”；不是重复电商案例，也不是只说“原理一样”。

### 9. 英文会翻译，语境意义错误

**请求**：代码里 `state` 我知道翻译成“状态”，所以它就是数据库里永久保存的业务状态，对吧？

**验证**：回到当前代码和数据生命周期确认指代；区分变量中的临时状态、协议状态和持久化业务状态；不因中文翻译相同就合并概念。

### 10. 连接模型与处理模型

**请求**：如果已经确定是连接池耗尽，接下来做什么？这套处理对所有数据库慢查询都适用吗？

**验证**：在判别成立后才进入处理；明确输入、动作、输出证据和边界；不把诊断方法与修复方法混为一谈。

### 11. 结构性新增必要性

**请求**：已有稳定的“关联工单为空”条件，还要不要新增“是否已建单”复选框？

**验证**：检查失败、唯一职责、替代性、删除后果和验收证据；现有条件稳定表达同一约束时判为冗余；说明什么变化会改变结论。

### 12. 语言材料不能只摘要

**请求**：帮我学这篇 RAG 文章。我不想只看摘要，以后遇到新的召回问题也要会判断。

**验证**：把最终任务改写成未见问题判断；从文章中找对象层、判别条件、输入输出和边界；摘要只作材料，不作完成证据；设计未见召回案例。

## 跨 Skill 路由案例

### R1. 纯概念理解

**请求**：MCP 和 API 有什么区别？我只想先判断不同项目里它们各自负责什么。

**期望路由**：使用 `explain`；完成标准是能判断未见案例，不要求搭建服务。

### R2. 从理解转向跑通

**请求**：API 我已经理解了，现在带我亲手接一个真实接口，能独立看文档、处理鉴权和报错。

**期望路由**：切换到 `pao-tong`；概念只使用“对象 → 意义 → 判别 → 当前作用”的精简循环。

### R3. 操作中追问因果

**请求**：继续教我配置飞书自动化。但先解释为什么要新增这个复选框，现有字段不能替代吗？

**期望路由**：仍由 `pao-tong` 管理真实任务和操作节奏；暂停点击，调用与 `explain` 一致的结构性新增判断；解释成立后继续操作，不开启两套重复流程。

## 总体通过标准

1. 先识别最终任务、当前语境和用户卡在哪一层；
2. 固定对应、判别模型、连接模型和程序性能力采用不同材料与验收；
3. 语言翻译、定义复述和原案例成功不被当作掌握；
4. 正例、反例和边界例服务于具体判断条件；
5. 区分内涵与判别、识别与处理、知识与决策；
6. 迁移时说明输入空间、不变关系、变化角色和验证方式；
7. 适合泛化的任务使用表面不同的未见案例；
8. 失败后给出具体诊断和对应修复，不统一“再解释一遍”。
