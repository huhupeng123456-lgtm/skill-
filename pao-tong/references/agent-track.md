## 适用范围

用于 Prompt、RAG、知识库、MCP、工具调用、Workflow、Agent 编排、Eval、Trace、记忆、Guardrail 和人工审批等能力。

## 从业务闭环定义目标

先在内部定义用户最终要独立构建或诊断的闭环：业务输入、Agent 判断、工具或数据源、结构化结果、风险阻断或人工确认、Trace 与评测证据。

需要向用户解释实际数据流时，不输出竖向箭头链，按当前项目填充：

| 步骤 | 发起方 | 接收方 | 传递内容 | 接收方动作 | 返回或状态变化 |
|---|---|---|---|---|---|
| 1 | 真实组件名 | 真实组件名 | 实际字段与本轮示例值 | 可观察的处理动作 | 完整返回或明确状态 |

每一行只表示一次传递。服务完整返回、SDK 解析后的对象和终端筛选显示属于不同状态，必须拆开；没有实际证据的字段标记为未知，不得补写。

仅能生成一段看似合理的回答，不算 Agent 闭环跑通。

## 责任分层

训练时要求用户能够区分：

- **Prompt 或 Skill**：负责目标、判断规则、输出契约和工具选择指导；
- **搜索、API 或数据库**：提供会变化的外部事实和业务数据；
- **程序硬规则**：执行不能交给模型自由判断的校验、阈值和状态约束；
- **人工确认**：处理高风险、不可逆、付费、发布或外部沟通动作；
- **Trace 与 Eval**：记录输入、工具调用、来源、版本、失败位置和评测结果。

发现用户把全部规则塞进 Prompt、把静态示例当实时数据，或把“有链接”当验证时，先纠正责任边界再继续。

## 协议与网络概念的讲解顺序

用户尚未建立网络调用模型时，不直接使用“A2A 客户端向 Agent 发送请求对象”“Agent 调用 8003 MCP”这类压缩表达。按以下顺序逐层建立：

1. **运行中的程序**：先指出当前有哪些 PowerShell 窗口，各自运行哪个 Python 文件或模块；
2. **端口**：说明端口只是操作系统分配给运行中程序的数字入口，例如当前项目的 `5007` 与 `8003`；
3. **完整地址**：拆开主机、端口和路径，例如 `http://127.0.0.1:8003/mcp`，不得把 `8003` 单独称为 MCP；
4. **协议**：说明协议是通信双方共同遵守的数据格式和交互规则，并区分当前链路中 A2A 与 MCP 各自约束哪两方；
5. **客户端与服务端**：说明它们是一次通信中的发起方和等待方角色，同一个 Agent 在 A2A 一侧可以是服务端，在 MCP 一侧可以是客户端；
6. **请求数据**：展示当前项目实际字段，例如 A2A Task 的 `id`、`message.role`、`message.content.text`，再说明程序对象序列化为 JSON 后通过 HTTP 发送；
7. **返回与证据**：区分 HTTP 状态、A2A Task 状态、MCP 工具结果、终端筛选显示和日志证据。

每次只解释当前步骤依赖的最小层级，并让用户先判断一个具体实例，再继续下一层。优先读取真实代码、请求、日志和端点返回，不用抽象类比替代项目证据。

讲状态变化时，从当前窗口能观察到的动作开始。多个组件同时出现时重复组件名，不用“它”串联。例如，面对缺少票数的输入，按下面的顺序讲：

> 5007 订票 Agent 收到这句话后，先检查日期、车次、座位和数量。输入里没有数量，所以 5007 订票 Agent 停止处理，没有联系 8003 MCP 票务服务。5007 订票 Agent 随后把本次任务标记为 `input-required`，意思是还需要用户补充信息。发送任务的测试程序读到这个标记后，把“缺少数量”显示在第三个窗口。

只有用户继续追问“这个标记放在哪里”时，才展示返回数据中的两个字段：

```json
{
  "status": {
    "state": "input-required",
    "message": {
      "content": {
        "text": "[MOCK] 缺少参数：数量（如 1张）"
      }
    }
  }
}
```

紧接着说明：`status.state` 记录任务当前进行到哪一步，`input-required` 表示等待用户补充信息；`status.message.content.text` 保存要显示给用户的具体原因。发送任务的测试程序读取这两个字段，所以第三个窗口能够同时显示任务进度和缺少的内容。

只有用户继续追问“为什么两个程序都认识这些字段”时，再补一句：A2A 是主程序与专业 Agent 之间的通信规则，它规定返回数据里使用 `status.state`，也规定 `input-required` 是可用值之一。不要提前追加“A2A 不负责发现缺少数量”之类防御性说明；用户没有混淆责任时，这句话只会增加新的理解负担。

## Mock 转向真实实现

先确定用户要掌握的真实能力，再判断 Mock 能否进入训练。Mock 替代核心能力时，只验证外围链路，不训练替代逻辑本身。

### 大模型判断被规则替代

规则程序替代意图识别、查询改写、工具选择或总结时，只能证明规则输出之后的路由、调用和解析能够运行。不能据此验收：

- 自由表达和多轮指代能否被正确理解；
- Prompt 是否有效；
- 模型输出是否稳定满足 JSON 契约；
- 模糊、冲突、越权或提示注入输入怎样处理；
- 模型质量、延迟、费用和版本变化。

最小 Mock 首次跑通后，优先转向以下真实任务之一：

1. 使用用户已有的授权模型 API；
2. 在硬件允许时运行本地模型；
3. 使用官方沙箱或测试额度；
4. 编写真实 Prompt、JSON Schema 和不少于三个代表性评测输入，再用真实模型验证；
5. 若模型仍不可用，明确把“模型理解与查询改写”标记为阻塞，只继续验收路由、契约和日志。

不要让用户反复修改只为规则 Mock 服务的关键词、正则表达式和命令参数，除非用户正在学习确定性解析或测试替身设计。

### 工具或数据源被静态结果替代

静态工具结果只能证明 Agent 会发起调用并读取返回。转向真实开发前，至少补齐真实接口定义、认证方式、字段映射、超时与重试、幂等性、错误码、审计日志和高风险人工确认中的相关部分。没有真实库存、数据库或业务 API 时，不验收数据准确性和业务成功。

### 面向真实开发或求职迁移

用户明确以开发落地或求职为目标时，训练重点放在可解释、可复核、可迁移的工作上：

- 说明为什么把某项判断放在模型、程序、工具或人工环节；
- 写出真实输入输出契约和失败分支；
- 修改并解释一处会进入真实方案的 Prompt、配置、代码或测试；
- 用 Trace、日志或评测结果证明判断；
- 说明当前实现距离生产还缺什么以及下一步怎样替换。

面试表达只能来自这些已完成证据，不把 Mock 成功包装成真实模型、真实数据或生产系统经验。

### IDE 中的多服务 Agent 项目

老师或真实团队使用 IDE 开发多服务 Agent 项目时，为主程序、各 Agent、MCP 服务和一次性测试分别创建具名运行配置。每个配置至少明确：

- 使用哪个项目解释器；
- 运行哪个模块或文件；
- 工作目录是什么；
- 需要哪些程序参数和环境变量；
- 运行后在哪个窗口看日志，怎样停止和重启；
- 服务占用哪个端口，端口冲突时去哪里判断。

让用户从 IDE 的运行配置选择并启动组件，不长期复制终端命令。终端保留给依赖安装和区分性诊断。至少安排一次 IDE 断点或变量检查，让用户观察主程序怎样选择 Agent、怎样构造参数或怎样处理返回值。

### 多组件的等价机制去重

对多个使用相同框架和调用模式的 Agent、MCP 服务或数据工具，首个组件完整训练“配置、启动、调用、读取返回、查日志和故障恢复”。后续组件先做差异检查：

- 若只改了端口、工具名、表名或业务字段，不重复同样的启动和直连测试教学；
- 若新组件改变了协议、认证、参数结构、返回状态、数据权限、可逆性或失败处理，只训练这些新差异；
- 若必须确认完整链路集成，只运行一次最小端到端用例，不再从工具列表、单工具调用和同类故障逐层重复；
- 用户选择跳过时，保留“机制已掌握，该组件未单独验证”的真实边界。

## 最小真实任务

任务至少包含：

1. 明确的业务输入与结构；
2. 可检查的 Agent 判断或路由；
3. 至少一个真实工具、授权数据源或明确标记的 Mock；
4. 结构化输出契约；
5. 一个异常、缺失或边界输入；
6. 一个风险阻断、回退或人工确认点；
7. 可读取的 Trace、日志或评测结果。

使用动态事实时记录来源、查询时间和未知项。使用 Mock 时说明替代了什么能力，禁止声称已经验证真实生产效果。

## 陪练方式

- 让用户先画清输入、判断、工具、输出和风险边界，再进入配置或代码。
- 每次只搭建或验证一个环节，并读取真实返回值或 Trace。
- 让用户说明当前变量、字段、工具参数和结果如何变化。
- 可以协助生成脚手架或示例，但核心路由、规则、验收和故障判断由用户完成。
- 跑通后逐步撤掉配置示例，让用户在新场景中重新选择工具和规则。

## 变式练习

选择一个会改变 Agent 行为的重要条件：

- 输入信息不完整、相互冲突或超出范围；
- 工具返回为空、超时、权限不足或数据过期；
- 更换数据源、模型、Prompt 版本或输出结构；
- 高风险动作从允许执行改为必须人工确认；
- 同一目标切换到新的业务对象或规则集。

要求用户预测 Agent 应如何路由、回退和留痕，再运行并核对 Trace。

## 故障练习

优先选择可观察、可恢复的问题：

- 工具 schema、参数名或返回字段不匹配；
- RAG 未召回、召回错误或引用无法回溯；
- Prompt 与程序规则冲突；
- 输出格式校验失败；
- Trace 显示工具未调用、调用失败或被错误重试；
- 人工确认、权限或 Guardrail 未生效。

让用户从 Trace 或日志定位失败所在层，再提出一个最小修复和回归验证。不要先给结论再让用户照抄。

## 独立挑战

给出同类但不同业务输入、工具状态或风险条件，只提供：

- 业务目标和成功标准；
- 可用工具与权限边界；
- 必须覆盖的正常、异常和风险场景；
- 需要提交的配置、输出、Trace 和评测证据。

用户独立完成后，要求其说明：

- 为什么把规则放在 Prompt、程序、工具或人工环节；
- 工具失败时如何回退；
- 哪些证据证明结果可信；
- 当前闭环距离生产运行还缺什么。
