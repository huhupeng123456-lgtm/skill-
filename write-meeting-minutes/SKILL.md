# 正式会议纪要

将会议原始材料转成领导可以快速决策、团队可以直接执行、后续可以复盘验收的正式纪要。先保证决策完整和权责清楚，再压缩表达；不要用金句、观点摘录或讨论过程填充篇幅。

处理任何会议纪要前，必须完整阅读：

- [references/decision-and-action-rules.md](references/decision-and-action-rules.md)：决策、行动项、优先级和遗漏检查规则。
- [references/output-template.md](references/output-template.md)：四段式交付结构和写作要求。

## 一、确定输入与来源

优先使用完整逐字稿：

1. 用户提供逐字稿、会议记录、文档或粘贴文本：直接读取全文。
2. 用户提供飞书会议或妙记链接：先读取本机 `lark-shared`、`lark-vc`、`lark-minutes` Skill，再取得完整逐字稿；不要只依赖飞书 AI 总结。
3. 用户提供本地音视频：通过 `lark-minutes` 生成妙记并取得逐字稿，再进入分析。
4. 用户只提供飞书 AI 总结、零散笔记或已有纪要：可以整理，但必须标注“来源不含完整逐字稿，可能存在决策遗漏”。
5. 用户要求审校已有纪要：同时读取原始逐字稿和已有纪要，先列漏项与错项，再交付修订后的完整纪要。

不要用常识、个人记忆或其他项目经验补齐会议没有说过的事实。

## 二、建立会议语境

通读全文后识别会议主题、日期、参会人、会议目标、核心议题和议题间依赖。

统一专业术语和项目名称，同一事项全篇只使用一个名称。明显转写错误可以统一修正；无法确认的人名、数字、日期和专有名词保留原文并标注 `[转写待确认]`。

### 建立说话人身份表

逐字稿使用“说话人 1、说话人 2”等编号时，必须先建立内部身份表，再提取责任分工。身份依据按以下优先级使用：

1. 用户在当前对话中的明确确认；
2. 发言人自报姓名或明确说“我是 XX”；
3. 其他参会人对其进行无歧义的点名或称呼；
4. 已有参会人名单与发言内容能够唯一对应。

高优先级证据覆盖低优先级转写。无法唯一对应时保留说话人编号并标注 `[姓名待确认]`，不得猜测姓名。用户已确认某个编号后，纪要中的责任人、行动项和证据账本必须统一使用该姓名，不得继续写“项目负责人”或说话人编号。

### 长会议必须分段覆盖

会议超过 30 分钟或逐字稿超过 10,000 字时，不得只按主题或关键词通读。先运行：

```bash
python scripts/meeting_coverage.py <transcript-file>
```

没有本地文件时，按脚本同等口径人工建立 10 分钟时间窗。每个时间窗都要有“已检查”记录，即使该时间段没有形成决策。脚本只用于暴露身份、分工、决策、文档变更、行动和风险候选，不能代替语义判断。

## 三、先建候选账本

不要边读边写纪要。第一轮扫描全文，建立内部候选账本：

- 说话人身份与证据；
- 决策候选；
- 待确认、待对齐事项；
- 行动项候选；
- 责任分工候选；
- 会后需修改的 PRD、需求表、方案、看板或其他下游文档；
- 遗留争议；
- 明确后置到下次讨论的议题；
- 重要项目的风险点。

候选阶段从宽收集，不要因为表达口语化、内容分散或缺少原因而删除。每条候选在内部保留发言人、时间戳或原文片段，正文默认不展示大段证据。

严格按照 `decision-and-action-rules.md` 判断状态和优先级。

## 四、完成第二轮决策完整性扫描

重新扫描全文，专门检查：

1. 每个议题最终形成了什么结论，还是仍未决定；
2. 是否出现方案选择、范围调整、优先级变化、时间变化、责任分配、资源承诺、验收口径或流程改变；
3. 是否有领导指示、多人确认、否决或撤回的方案；
4. 同一事项前后结论是否变化；
5. 是否有行动项找不到对应决策或明确指令；
6. 是否有已拍板事项因为没有说明“为什么”而被遗漏。
7. 每个“你负责”“你跟 XX 做”“我们一起做”“分给 XX”“这个模块由 XX”等责任分配是否独立入账；
8. 最后 20% 的逐字稿是否出现总结、重新分工、撤回或替代前文结论；
9. 每位被点名承担工作的参会人是否至少对应一条责任或行动候选；
10. “写进 PRD”“需求表补上”“文档改掉”“模块删掉”等指令是否进入下游文档变更账本。

发生前后冲突时，以最后一次明确确认的内容作为当前结论；无法判断最终状态时列入待确认或遗留争议，不得自行选择。

责任分配必须保持原子性。不同责任人、不同业务模块或不同交付成果不得因为发生在同一段对话中而合并。例如“管理端数据统计”和“客服配置”即使同时分配，也要分别核对责任人、范围和交付物；只有三者完全相同才可在正文合并展示。

## 五、固化行动项三要素

只把明确承诺、明确指派或决策必需的后续动作写入行动项。

每条行动必须同时具备：

1. **负责人**：明确到具体人员，不写“相关人员”“团队负责”。
2. **截止日期**：精确到 `YYYY-MM-DD`，不写“尽快”“后续”“近期”。
3. **交付成果**：写清具体产出，例如文档、方案、清单、系统版本或评审会。

缺少任一要素时：

- 不得猜测或补造；
- 在行动项中标注 `[待确认]`；
- 同时把缺失字段加入“待确认、待对齐的疑问点”；
- 该行动在要素补齐前不得标记为可直接执行。

推荐表达：“XX 于 2026-07-25 输出 AI 优化方案 V1.0，并同步项目群评审。”

## 六、压缩并排序

不要逐字抄对话，只提炼会改变决策、执行或后续讨论的有效内容。

默认删除：

- 寒暄、开场白和结束语；
- 争论过程、重复发言、附和和情绪表达；
- 不改变决策或行动的普通进度同步；
- 金句、精彩观点、启发点和案例分享；
- 与会议目标无关的发散讨论；
- 没有事实、决策或执行价值的正确废话。

不要为了简短删除独立决策。多条表达同一决策时合并，但保留适用范围、条件和例外。

## 七、按四段式生成正式纪要

严格按 `output-template.md` 交付：

1. **本次会议核心结论 / 决策**：标题之后立即出现，全文重点全部前置。
2. **待确认、待对齐的疑问点**：集中展示阻碍执行的信息缺口和需要确认的口径。
3. **所有落地行动项**：逐条列明负责人、截止日期和交付成果。
4. **遗留争议、下期待讨论议题**：放在末尾，避免干扰已定结论。

标题必须同时包含会议主题、日期和参会人。正文不另设“会议背景”“会议过程”“金句”等章节。

重要项目：

- 为关键决策和行动项标注 P0/P1/P2；
- 在第一部分单独高亮重大风险；
- 风险必须说明影响对象和触发条件，不写空泛提示。

默认只交付一份可直接使用的完整纪要，不让用户自行拼接。原文证据保留在内部账本；只有用户要求审计、复核或追溯时才输出证据附录。

## 八、交付前门禁

逐项检查：

- 领导是否只看第一部分就能掌握会议重点；
- 每个明确决策是否都进入纪要；
- 已定、待确认和遗留争议是否混淆；
- 前后变化是否采用最后确认结果；
- 每条行动是否同时包含具体负责人、精确日期和明确交付成果；
- 所有缺失行动要素是否同步进入待确认区；
- 专业术语和项目名称是否全文一致；
- 是否残留金句、对话过程、重复内容或无关进度；
- 是否存在模型补写的原因、期限或责任人；
- 来源不完整时是否明确提示遗漏风险；
- 长会议的每个 10 分钟窗口是否均已检查；
- 说话人身份是否按证据优先级完成映射并全文统一；
- 每条明确责任分配是否独立进入候选账本；
- 每位被点名承担工作的参会人是否在责任或行动项中有对应记录；
- 会议末段的总结和重新分工是否与正文逐条对账；
- 所有明确要求修改的 PRD、需求表、方案和看板是否进入文档变更或行动项；
- 纪要能否直接用于后续复盘、追责和验收。

正式中文材料交付前，如 `humanizer-zh` 可用，使用其写作模式检查表达，只调整措辞，不改变任何事实。

## 多会议处理

用户要求处理多场会议时：

1. 每场会议分别执行完整流程并分别成文；
2. 再按需生成跨会议汇总；
3. 跨会议汇总只保留新增决策、决策变化、未补齐行动、逾期行动、重大风险和跨会议争议；
4. 不用会议数量或链接列表代替纪要内容。
