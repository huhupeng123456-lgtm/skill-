# 会议知识提取器

从会议或课程文字稿中深度提取真正的知识——不是表面的信息整理，而是能沉淀下来、指导后续行动的内容。

## 核心原则

### 只提取三类信息

忽略所有以下内容：
- 客套话、寒暄、开场白、结束语
- 简单的进度确认（"好的"、"明白"、"没问题"）
- 纯信息同步（"我们做了XX"、"进度到XX%"）
- 重复性陈述、附和性发言

只保留以下三类：

**1. 非共识观点**
- 与常规直觉相反的判断
- 反常识的结论或做法
- "一般人会这样想，但实际上..."类的发言

**2. 决策背后的"为什么"**
- 不要只记结论，要记为什么这么选
- 当时放弃了什么选项？为什么没选？
- 这个决策的约束条件和假设前提是什么？

**3. 具体的执行细节**
- 踩过的坑和教训
- 具体的数字、比例、阈值
- 特定的方法论或操作流程
- 某一步是怎么做的，用了什么工具/技术

### 强制要求：每条附带原文

提取任何知识点时，**必须附带一段对话原文**。目的是：
- 防止 AI 为了显得有逻辑而自己编造"正确的废话"
- 强制回到当时的语境，不做过度概括
- 让用户能回溯、验证、深挖

原文引用规则：
- 直接引用发言原话，加引号
- 如原文过长，用 "..." 省略次要内容，保留关键信息
- 标注发言者（如已知）
- 不得改写原文意思，不得添加原文没有的信息

## 触发条件

当用户行为满足以下任一条件时激活：
- 提到"会议记录"、"会议纪要"、"课程笔记"、"学习笔记"、"文字稿"、"提取知识"
- 上传或引用包含会议/课程文字的文档（txt/docx/md 等）
- 粘贴大段会议/课程转录文字

## 输入处理

1. **文件输入**：使用 Read 工具读取用户提供的文档内容
2. **文本输入**：直接处理用户粘贴的文字
3. **预处理**：
   - 识别发言者标记（如"张三："、"[李四]"、"@王五"等）
   - 识别语音识别错误：同一产品/人名出现多种写法时，在术语表中统一标注
   - 去除口语填充词，保留语义

## 分析工作流

### 第一步：通读全文，建立语境

快速浏览全文，理解：
- 这是什么类型的会议？（技术评审、项目汇报、需求讨论、课程分享）
- 参与者有哪些角色？（开发、PM、客户、领导）
- 讨论的核心议题是什么？
- 会议的最终结论或待办是什么？

**不要在这个阶段做任何提取**，先建立整体语境。

### 第二步：提取非共识观点

逐段扫描，寻找"反直觉"的内容：

**判断标准**：
- 如果一般人听到会说"原来还能这样"或"这跟我理解的不一样"
- 发言者明确提到"通常大家会...但我们..."
- 结论与行业常识、常规做法相反
- 从失败/教训中得出的反向认知

**提取格式**：
- 底层逻辑：这个观点挑战了什么常规认知？
- 具体做法：发言者建议怎么做？
- 启发点：对听众的工作有什么颠覆性启发？
- 原文依据：附上一段原文

### 第三步：提取决策背后的"为什么"

逐段扫描，寻找关键决策点：

**判断标准**：
- "我们选择了 A 而不是 B"
- "当时我们想过...但后来决定..."
- "之所以这样做是因为..."
- 产品选型、架构设计、路线选择的讨论

**提取格式**：
- 决策：最终选择了什么？
- 为什么这么选：核心原因和约束条件
- 放弃了什么：没被选的方案及其优缺点
- 原文依据：附上一段原文

### 第四步：提取具体执行细节

逐段扫描，寻找"可复现的操作指南"：

**判断标准**：
- 具体的数字、比例、阈值（"准确率 95%"、"超时 30 秒"）
- 踩坑记录和教训（"我们当时遇到了...后来发现..."）
- 具体的操作步骤（"第一步...第二步..."）
- 使用的工具、框架、方法名称
- 某一步的具体实现方式

**提取格式**：
- 底层逻辑：这个方法解决的核心问题是什么？
- 具体做法：具体怎么做的？用到什么工具/技术？
- 启发点：这个方法可以迁移到什么场景？
- 原文依据：附上一段原文

### 第五步：去重与验证

对提取的内容进行自检：
- 是否有内容看似是"执行细节"，实则是"常识"？（删除）
- 是否有"决策 Why"没有说明"放弃了什么"？（补充）
- 是否有"非共识观点"缺少原文支撑？（补充或删除）
- 是否有内容是自己脑补的，原文中没有？（删除）

## 输出规范

严格按照 [references/output-template.md](references/output-template.md) 的格式输出。

### 输出格式要求

使用**表格**输出，表头固定为：

```
| 底层逻辑 | 具体做法 | 启发点 | 原文依据 |
|----------|----------|--------|----------|
```

**非共识观点**和**执行细节**使用四列表格。
**决策背后的为什么**使用四列表格，表头为：

```
| 决策 | 为什么这么选 | 放弃了什么 | 原文依据 |
|------|-------------|-----------|----------|
```

### 质量约束

1. **不确定不编造**：无法确认的信息，标注 `[需确认]` 而非猜测
2. **强制原文**：每条知识点必须附带一段原文引用，无原文则删除
3. **去常识化**：不要提取"正确的废话"，如"测试很重要"、"用户体验很重要"
4. **去概括化**：不要用自己的话"总结"观点，保留原文语境
5. **大白话解释**：专业术语只在必要时解释，且必须让非技术背景的 PM 能看懂

## 在线文档预留

如用户提供飞书/腾讯文档/钉钉等在线文档链接：
1. 告知用户当前版本暂不支持直接读取在线文档
2. 引导用户将内容导出为 txt/docx 或复制粘贴
3. 未来扩展：可通过配置 API 接入在线文档平台

## 注意事项

- **不要输出摘要或总结**，专注于深度知识提取
- **不要输出"发言者画像"**，除非该发言人的身份/角色对理解内容至关重要
- **不要输出"行动启发"**作为独立章节，有价值的行动点嵌入执行细节的"启发点"列
- 如内容涉及敏感信息（客户名称、内部数据），在输出中保持脱敏处理
- 输出控制在合理长度，**宁缺毋滥**——宁可少提取几条，也不要凑数
