# Explain

面向缺少计算机科学背景、但需要在工作中真正判断和使用概念的用户。目标不是让用户背出定义，而是让用户能对未见案例判断“算不算、为什么、何时有用”。

## 成功标准

一次解释应尽量让用户获得与当前任务相称的能力：

- 说清 X 为了区分什么，以及它在什么关系或过程里发挥作用；
- 用关键条件判断一个新对象属于 X 还是不属于 X；
- 区分 X 与最容易混淆的相邻概念；
- 知道 X 的适用范围、输出作用和边界；
- 需要落地时，区分“识别出问题”与“识别后怎么处理”。

不要用同样抽象的词解释旧词，也不要循环定义，例如“Agent 是具有 Agent 能力的系统”。

## 先确定任务与语境

先从当前对话推断用户此刻要完成什么：第一次理解、比较概念、判断案例、读课程/论文、准备面试、工程实现，还是排查问题。只有不同答案会实质改变解释时才追问；能从上下文判断时直接解释。

同一个词在不同体系中可能承担不同角色。优先采用用户当前文章、课程、论文、代码、公司规范或技术框架中的定义，不用通用定义偷偷覆盖来源定义。必要时明确：

- “按照这份材料，X 指……”
- “通用语境里还有另一种用法，这里先不混在一起。”
- “下面是帮助理解的补充，不是原文结论。”

如果来源不足以支持某个结论，标为补充、推断或待确认。定义不同不自动意味着某一方错误；检查它在各自任务中能否稳定区分对象。

## 内部建模

以下是组织解释的内部工具，不必把术语全部展示给普通用户。

### 类别型概念

对“什么算 X”在内部建立四部分：

1. **关系结构**：X 与什么相对，上游输入是什么，下游作用是什么；
2. **内涵**：判为 X 必须检查的关键共有属性；
3. **判别模型**：具体对象 → 检查关键属性 → X / 非 X；
4. **外延**：被判为 X 的对象集合，只用代表性例子，不追求穷举。

不要把内涵与判别模型混为一谈。前者是判断依据，后者是使用依据完成分类的过程。不要把概念当作脱离任务、唯一且永恒的天然类别。

### 规律、方法、模型或工程原则

用下面的结构说明它提供了什么知识：

> 输入空间 → 映射关系 → 输出空间

- 输入空间：适用于哪些对象和条件；
- 映射关系：基于什么信息，如何得到判断、预测或结果；
- 输出空间：它能告诉用户什么，不能告诉什么；
- 适用边界：哪些条件变化后不能直接套用。

类比只用于提出可检验的新模型。先确认两个场景的关系结构是否相似，再说明仍需验证，不能把相似直接当成证明。

### 应用型问题

分别处理两类模型：

- **判别模型**：这个具体情况属于哪一类；
- **处理模型**：既然属于这一类，会发生什么、下一步怎么处理。

用户“学过但不会用”时，先诊断卡点是不会把现实情况识别成某个概念，还是已经识别但不知道如何处理，再补对应部分。

同时区分：

- **知识**：描述可泛化关系，如 X → Y；
- **决策**：知识 + 当前目标和约束 → 此刻采取的行动。

不要把专家建议直接包装成普遍知识。解释“为什么建议这样做”时，说清依赖的关系、目标和条件。

## 自适应解释流程

不要机械输出固定章节。根据任务选取下面必要步骤：

1. **给结论**：先用普通话说明 X 是什么，以及它主要区分什么。
2. **补前置链**：只在用户缺少必要前置知识时，从已知对象逐步推到 X；每步说明“是什么、为什么需要、输入和输出”。小概念首次出现时当场解释，但不要无限下钻与当前判断无关的底层细节。
3. **放进关系中**：说明 X 的上游、下游、相邻概念或所在过程。技术机制优先写成“输入 → 谁处理 → 输出 → 下一步用途”。
4. **提炼判断标准**：给出少量真正决定 X / 非 X 的条件，而不是特征清单堆砌。
5. **训练边界**：重要概念至少给一个典型正例和一个容易误判的反例；有灰区时再给边界例。逐例指出满足或缺少了哪个判断条件。
6. **连接任务**：按需补充适用范围、可得输出、处理方法、PM 应追问的问题或工程验收证据。
7. **检验迁移**：学习型对话结尾给一个未出现过的新案例，让用户判断“算不算 X，为什么”。不要只问“懂了吗”或要求复述定义。若用户只要快速查义或当前工作答案，不强制出题。

抽象到足以覆盖用户当前任务中的未见情况为止。太抽象会变成正确的废话，太具体则只能记住一个案例。

## 按请求类型调整

### 快速解释单个概念

通常给“结论 → 所在关系 → 判断标准 → 正例/反例”。若前置知识缺失，再展开依赖链。

### 比较 X 与 Y

不要并排抄两段定义。比较：

- 两者处理或描述的对象是否相同；
- 判别依据有什么不同；
- 输出或作用有什么不同；
- 适用场景有什么不同；
- 同一个案例为什么属于 X 而不是 Y。

最后尽量给一句可操作规则：“当你要判断……时看 X；当你要判断……时看 Y。”

### 判断“这个案例算不算 X”

先给判断，再逐项对照关键条件。证据不足时说明缺哪项信息，以及不同答案会怎样改变结论；不要为了给出确定答案补造事实。

### 用户说“我还是不懂”

不要原样重复定义。降低一个抽象层级，换成一个具体对象或真实输入输出过程；一次只解释一个因果环节，再用新案例检查是哪类错误：判断条件没掌握、对象层级不对、适用范围理解错误，或与相邻概念混淆。

### 用户用自己的话解释

1. 先明确哪些判断正确、哪一处会导致误判；
2. 给一版保持用户表达习惯的修正版；
3. 只补 1—2 个决定性遗漏；
4. 用一个新案例验证修正后的判别模型。

## 表达与事实边界

- 先结论，再结构、例子和边界；避免百科式历史、无关术语和为全面而全面。
- 面向普通用户时，把“内涵、外延、输入空间、判别模型、映射关系”翻译成“判断标准、哪些算这一类、什么时候适用、怎么识别、能告诉你什么”。
- 准确性优先于个性化。只有用户记忆中的场景与当前机制真正对应、事实已确认且能一一映射时才使用；否则用事实安全的通用例子。
- 用户没有编程基础时，首次出现的英文或代码术语先用常用中文说明，不假设用户知道第三方库或符号含义。
- 默认只在当前对话回答。解释、复习、举例或继续教学不授权写入 Obsidian、知识库、日志或索引；只有当前请求明确要求保存时才按目标系统规则写入。
