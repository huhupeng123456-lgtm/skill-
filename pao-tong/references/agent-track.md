# Agent 工程训练轨道

## 适用范围

用于 Prompt、RAG、知识库、MCP、工具调用、Workflow、Agent 编排、Eval、Trace、记忆、Guardrail 和人工审批等能力。

## 从业务闭环定义目标

先在内部定义用户最终要独立构建或诊断的闭环：业务输入、Agent 判断、工具或数据源、结构化结果、风险阻断或人工确认、Trace 与评测证据。

需要向用户解释实际数据流时，不输出竖向箭头链，按当前项目填充：

| 步骤 | 发起方 | 接收方 | 传递内容 | 接收方动作 | 返回或状态变化 |
|---|---|---|---|---|---|
| 1 | 真实组件名 | 真实组件名 | 实际字段与本轮示例值 | 可观察的处理动作 | 完整返回或明确状态 |

每一行只表示一次传递。服务完整返回、SDK 解析后的对象和终端筛选显示属于不同状态，必须拆开；没有实际证据的字段标记为未知，不得补写。

仅能生成一段看似合理的回答，不算 Agent 闭环跑通。

## 责任分层

训练时要求用户能够区分：

- **Prompt 或 Skill**：负责目标、判断规则、输出契约和工具选择指导；
- **搜索、API 或数据库**：提供会变化的外部事实和业务数据；
- **程序硬规则**：执行不能交给模型自由判断的校验、阈值和状态约束；
- **人工确认**：处理高风险、不可逆、付费、发布或外部沟通动作；
- **Trace 与 Eval**：记录输入、工具调用、来源、版本、失败位置和评测结果。

发现用户把全部规则塞进 Prompt、把静态示例当实时数据，或把“有链接”当验证时，先纠正责任边界再继续。

## 最小真实任务

任务至少包含：

1. 明确的业务输入与结构；
2. 可检查的 Agent 判断或路由；
3. 至少一个真实工具、授权数据源或明确标记的 Mock；
4. 结构化输出契约；
5. 一个异常、缺失或边界输入；
6. 一个风险阻断、回退或人工确认点；
7. 可读取的 Trace、日志或评测结果。

使用动态事实时记录来源、查询时间和未知项。使用 Mock 时说明替代了什么能力，禁止声称已经验证真实生产效果。

## 陪练方式

- 让用户先画清输入、判断、工具、输出和风险边界，再进入配置或代码。
- 每次只搭建或验证一个环节，并读取真实返回值或 Trace。
- 让用户说明当前变量、字段、工具参数和结果如何变化。
- 可以协助生成脚手架或示例，但核心路由、规则、验收和故障判断由用户完成。
- 跑通后逐步撤掉配置示例，让用户在新场景中重新选择工具和规则。

## 变式练习

选择一个会改变 Agent 行为的重要条件：

- 输入信息不完整、相互冲突或超出范围；
- 工具返回为空、超时、权限不足或数据过期；
- 更换数据源、模型、Prompt 版本或输出结构；
- 高风险动作从允许执行改为必须人工确认；
- 同一目标切换到新的业务对象或规则集。

要求用户预测 Agent 应如何路由、回退和留痕，再运行并核对 Trace。

## 故障练习

优先选择可观察、可恢复的问题：

- 工具 schema、参数名或返回字段不匹配；
- RAG 未召回、召回错误或引用无法回溯；
- Prompt 与程序规则冲突；
- 输出格式校验失败；
- Trace 显示工具未调用、调用失败或被错误重试；
- 人工确认、权限或 Guardrail 未生效。

让用户从 Trace 或日志定位失败所在层，再提出一个最小修复和回归验证。不要先给结论再让用户照抄。

## 独立挑战

给出同类但不同业务输入、工具状态或风险条件，只提供：

- 业务目标和成功标准；
- 可用工具与权限边界；
- 必须覆盖的正常、异常和风险场景；
- 需要提交的配置、输出、Trace 和评测证据。

用户独立完成后，要求其说明：

- 为什么把规则放在 Prompt、程序、工具或人工环节；
- 工具失败时如何回退；
- 哪些证据证明结果可信；
- 当前闭环距离生产运行还缺什么。
