# 任务技能沉淀

把一次已经完成并有证据的任务转化为以后可重复调用、可验证、可维护的 Skill。先判断是否值得沉淀，再与用户共同确定抽象边界；不要为了产出 Skill 而创建 Skill。

## 核心约束

1. 先读取当前工作区及目标目录适用的 `AGENTS.md` 和项目规范；没有规范时，先确定目录、命名、发布和回退规则。
2. 只处理已完成或已有阶段性验收证据的任务。命令成功、请求已发出、文件已生成不能单独视为任务完成。
3. 只依据可访问的对话、产物、工具结果和用户确认。无法访问完整对话时明确缺口，不得声称已完整复盘。
4. 区分用户确认事实、工具观察、Agent 推断和未知项。推断不得写成稳定规则。
5. 每轮只确认一个关键决策，并同时给出基于证据的推荐项。允许用户改名、合并、拆分、换候选或终止。
6. 设置三道硬门禁：候选方向确认、Skill 契约确认、发布确认。未通过对应门禁，不进入下一阶段。
7. 不把客户名、人员、日期、账号、密钥、固定资源 ID、一次性路径、临时状态和本次正确答案固化进通用 Skill。需要示例时使用脱敏 mock。
8. 不自动写入 Memory、Obsidian、项目文档或 `AGENTS.md`。判断这些载体更合适时只提出建议，等待用户另行授权。
9. 不直接修改系统、插件或第三方托管 Skill。需要扩展时创建用户自有 Skill，并说明关联关系。
10. 不递归沉淀本 Skill 自己的运行过程，除非用户明确要求改进 `distill-task-skill` 本身。
11. 用户纠正是分析证据，不是可直接复制的结论。先复原“用户原意 → Agent 的错误理解或行为 → 用户不满 → 理解偏差”，再提炼通用规则；不得把最终修改清单、框架名称或示例原样包装成通用能力。
12. 用户或上级路由器指定 `current_project` 时，必须检查项目关联历史任务的用户纠正并记录来源覆盖；只读当前文件或当前会话不得声称已完整复盘项目。
13. 内部先建立完整纠正主题清单，再按影响、错误代价、重复程度、可迁移性和增量价值排序；最多展示三个候选不等于最多提取三个主题。

开始判断候选前，完整阅读 [references/distillation-rubric.md](references/distillation-rubric.md)。使用其中的证据分级、路由规则和三张确认卡；不要复制一套平行标准。

## 工作流

### 0. 锁定复盘对象

确认用户指的是哪个已完成任务或哪个阶段，并锁定 `source_scope`：`current_conversation`、`current_project` 或 `selected_sources`。优先从当前对话直接定位；存在多个相邻任务时，只问一个定位问题。

`current_project` 模式先识别项目根目录，读取项目规则和相关当前材料，再通过宿主任务索引或本地会话元数据按 `cwd`、工作树、明确项目路径或项目标识筛出同项目历史任务。随后从项目名称、产物文件名、任务类型和领域对象提取少量锚点，补查在其他工作目录完成但语义属于本项目的用户历史消息。

只把真实用户 query、纠正、拒绝、重写要求和验收反馈当作用户证据；排除宿主注入内容、项目规则转录、环境上下文和继承对话副本。按消息 ID、会话谱系和规范化内容摘要去重，分叉或重放中的同一条消息不能冒充跨任务重复。只有还原纠偏链时才读取对应 Agent 输出。

记录每类必需来源的 `inspected`、`unavailable` 或 `not_applicable` 状态。历史任务或关键验收证据不可访问时返回 `EVIDENCE_NEEDED` 或明确的部分结果，不得把当前文件冒充整个项目上下文。

部分结果只允许只读展示来源缺口和暂定主题。只要缺失来源可能改变失败根因、抽象规则、适用边界、去重结论或目标载体，就返回 `EVIDENCE_NEEDED` 并停止，不得进入候选方向确认、Skill 契约、研发或发布。

建立只读证据清单：

- 原始目标、真实输入和限制；
- 实际执行步骤、关键选择及理由；
- 失败尝试、对应的原始要求、用户纠正、修复与重试；
- 最终产物、测试结果和用户验收反馈；
- 仍未验证的判断与缺失材料。

若缺少能够证明任务闭环的证据，返回 `EVIDENCE_NEEDED`，列出最少需要补齐的证据，并停止创建流程。

同时建立现有 Skill 快速索引，覆盖当前项目 Skill 目录及宿主提供的用户全局 Skill 根目录。先比较 `name`、`description`、触发意图和主要输出，只深读最接近的用户自有 Skill。该索引用于在提取阶段判断 `duplicate`、更新现有或新建；归属或修改权限不明时返回 `OWNERSHIP_NEEDED`。

### 1. 提取可复用能力

先用明确纠正信号检索一轮，再围绕已发现的主题、读者、验收标准和失败模式做一轮语义扩展。把措辞不同但行为含义相同的反馈聚为一个主题；新一轮仍出现高价值主题时再检索一轮。三轮后仍持续出现新的高价值主题时，将来源标为部分结果并停在只读预览，不进入门禁 A。

先处理包含用户不满或纠正的证据。对每个能够核对的纠偏片段，记录：

- 用户原意：引用原话或做忠实释义，并区分内容要求、叙事逻辑和输出格式；
- 错误理解或行为：只描述实际答案、产物或操作中可观察的问题；
- 用户纠正：记录用户明确否定了什么、重新解释了什么；
- 理解偏差：说明 Agent 把哪一层要求误当成了哪一层要求；
- 通用规则：写成“在什么条件下，应怎样判断或行动”；
- 适用边界：说明什么明确信号出现时，应采用另一种处理方式。

不得从最终正确答案反推一个未经用户确认的失败原因。缺少原始要求、失败表现或用户纠正中的任一关键证据时，把原因标为未知，不写成稳定规则。

对拟议规则执行跨场景检验：至少替换成两个不同任务，确认规则仍能指导决策，而不是只会复述本次答案。若无法自然迁移，保留为任务特例或路由到其他载体。

从证据清单中提取：

- 可复用的操作步骤；
- 非显然的判断规则；
- 已验证的失败原因和恢复方法；
- 反复执行且适合脚本化的动作；
- 可复用的输出结构或模板；
- 可观察、可复验的完成标准。

把任务特例与通用能力分开：

- 保留未来如何再次得到正确结果的方法；
- 参数化会随任务变化的输入；
- 删除一次性结论和未验证推断；
- 将细节规则、案例和模板规划到 `references/`；
- 只把稳定、重复、需要确定性执行的逻辑规划到 `scripts/`；
- 只把最终输出直接复用的文件规划到 `assets/`。

当用户引用 STAR、金字塔原理、问题—方案—结果等框架时，先判断用户要求的是思考维度、叙事逻辑还是显式输出结构。只有出现“分栏、标题、字段、表格、逐项填写、按模板输出”等明确信号时，才把框架名称直接呈现为栏目；否则默认把框架隐含在自然表达中。详细判断与示例见参考文件的“理解偏差抽象”部分。

先为每个强纠正主题记录 `candidate`、`duplicate`、`other_carrier` 或 `ignore` 处置，再对合格候选排序。多次纠正背后的上位方法、高错误代价且能跨任务迁移的方法优先；单次措辞、栏目名称或局部格式修改优先作为上位方法的证据。

最多向用户展示三个候选，但内部强纠正主题必须全部有处置结果。若没有候选通过可复用性门禁，明确建议“不创建 Skill”，说明更合适的载体或还需积累什么证据，然后停止。

### 2. 候选方向确认（门禁 A）

按参考文件的“候选确认卡”展示候选，给出推荐排序和理由。存在用户纠正时，候选卡必须展示原意、错误理解、通用规则和适用边界；不得把“要沉淀什么”原样抛回用户，也不得复述最终修改清单冒充抽象结果。

一次只询问一个决策，例如：

> 本轮建议先沉淀候选 1，因为它已有完整验证证据且可跨任务复用。是否按这个方向继续？

仅在用户明确选择某个候选后继续。用户修正范围时，更新证据清单和候选卡，再次确认；不要把用户的修正仅记在回复中。

### 3. 复核现有 Skill 并决定新建或更新

复用步骤 0 建立的现有 Skill 索引，并针对用户已选候选复核当前项目 Skill 目录及存在的全局根目录，至少检查：

- `C:\Users\user\.codex\skills`
- `C:\Users\user\.agents\skills`
- `C:\Users\user\.claude\skills`
- 当前项目规则指定的 Skill 研发目录

若步骤 0 后出现新的可发现 Skill，先更新索引。再次比较 frontmatter 的 `name`、`description` 和触发意图，再读取最接近候选的正文。按以下规则路由：

- 未来触发语、用户目标和主要输出相同：更新现有用户自有 Skill；
- 只是增加故障处理、门禁、模板或参考资料：更新现有用户自有 Skill；
- 目标、主要输出、权限边界或核心流程明显不同：新建 Skill；
- 只包含偏好、项目规则、状态事实或一次性教训：建议其他载体，不创建 Skill；
- 现有 Skill 为系统、插件或第三方托管：不覆盖，创建用户自有扩展或停止。

发现高度重叠但归属、权限或正式版本不明时，返回 `OWNERSHIP_NEEDED` 并停止写入。

### 4. 定义 Skill 契约（门禁 B）

按参考文件的“Skill 契约确认卡”形成一份完整建议，至少包含：

- `name`、显示名和一句话目标；
- 正向触发语及不应触发的场景；
- 输入、输出和可观察的验收标准；
- 核心流程、权限边界和停止条件；
- 新建或更新的结论及证据；
- `SKILL.md`、`references/`、`scripts/`、`assets/` 的最小文件规划；
- 研发暂存路径、正式发布路径和回退方式；
- 正向、边界、负向和回归测试计划。

标出仍待确认项，并给出推荐默认值。用户每次修正后重发已更新的完整契约；只有用户明确同意整份契约，才允许创建或修改暂存文件。

### 5. 使用 skill-creator 暂存实现

找到并完整阅读已安装的 `skill-creator/SKILL.md` 及其要求的相关参考文件。缺失 `skill-creator` 时返回 `BLOCKED`，不要凭记忆重建创建流程。

遵循当前项目的研发与发布规则：

1. 新建 Skill 时必须运行 `skill-creator` 的 `init_skill.py`，不得手工伪造初始目录。
2. 更新现有 Skill 时先复制到研发暂存区，保留正式版本；不要直接在正式目录试改。
3. 只创建契约中确有用途的资源目录，不保留模板、TODO、README、变更日志或空目录。
4. 保持 `SKILL.md` 精简并控制在 500 行内；详细规则放一层 `references/`。
5. 生成或更新 `agents/openai.yaml`，确保显示名、简短说明和默认提示与 `SKILL.md` 一致。
6. 中文文件统一使用 UTF-8；在 Windows 上运行 Python 校验工具时优先启用 UTF-8 模式。
7. 使用局部补丁修改文件，保留工作区中与当前任务无关的用户改动。

若 `G:\codex skill\AGENTS.md` 存在，将 `G:\codex skill\skills\<skill-name>` 作为研发路径，并遵循该工作区规定的发布流程。否则，根据当前项目规范选择暂存路径；规范未指定时，向用户确认，不能把正式全局目录当作草稿区。

### 6. 校验与前向测试

至少完成以下检查：

1. 使用 `quick_validate.py` 校验结构、frontmatter、名称和 UI 元数据。
2. 检查无 TODO、占位示例、敏感信息、固定项目事实、重复说明和无依据强化结论。
3. 检查三条正向触发、三条负向触发以及信息不足场景。
4. 对含用户纠正的候选，检查是否完整呈现“原意、错误理解、通用规则、适用边界”，并用至少两个不同任务验证可迁移性。
5. 对新增脚本执行真实运行测试，不以静态阅读替代。
6. 使用最少上下文和原始任务输入进行独立前向测试；测试 Agent 只看到待测 Skill 和原始请求，不得看到预期答案、问题诊断或拟议修复。
7. 使用 mock 数据隔离外部写入、生产系统、费用和客户敏感信息。测试可能产生外部影响时，先取得单独许可。
8. 更新已有 Skill 时复跑原有代表场景，确认没有能力退化。

任何必需测试失败时，保留研发稿并进入修正循环；不得进入发布确认。最多连续修正三轮仍无法通过时返回 `BLOCKED`，列出失败证据和推荐动作。

### 7. 发布确认（门禁 C）

按参考文件的“发布确认卡”向用户展示：

- 文件树或更新差异；
- 各项校验与前向测试证据；
- 已知限制和未覆盖场景；
- 正式目标路径；
- 同名正式版本的备份路径和回退方法。

仅当用户明确表示“发布”或同等含义时执行发布。用户要求继续修改时回到实现与测试；用户要求保留草稿或放弃时，不改正式版本。

### 8. 发布、读回与冒烟测试

发布时：

1. 再次解析并核对正式目标的绝对路径。
2. 若存在同名正式 Skill，先复制到带时间戳的回退目录，并确认备份可读。
3. 将通过测试的准确暂存状态发布到正式目录。
4. 读回正式 `SKILL.md`、`agents/openai.yaml` 和资源清单，确认与暂存版本一致。
5. 对正式副本再次运行 `quick_validate.py`。
6. 在干净上下文中执行一次真实触发冒烟测试。

发布失败、读回不一致或正式副本测试失败时，恢复备份；没有旧版本时保留研发稿并清理不完整正式目录。报告实际结果，不声称发布成功。

### 9. 交付回执

以 `DONE`、`DONE_WITH_CONCERNS`、`EVIDENCE_NEEDED`、`OWNERSHIP_NEEDED` 或 `BLOCKED` 开头，简要交付：

- 最终判断：新建、更新、不沉淀或转其他载体；
- 已确认的适用边界；
- 研发与正式路径；
- 校验、前向测试和冒烟测试结果；
- 备份与回退信息；
- 仍待用户决定的唯一下一步。

不要把“Skill 文件已生成”等同于“能力已经验证”。只有正式副本读回和冒烟测试通过后，才能报告发布完成。
