# 已验收示例：解释下，什么是 Agent？

## 用途

这个示例来自用户真实的最短问法，并已得到用户认可。它用于评估：当用户没有主动提供课程定义、比较对象或案例时，Agent 能否直接选择合理语境，建立判断标准，并帮助用户迁移到新案例。

学习回答的任务判断和结构，不要机械复刻措辞，也不要把这里的 Agent 定义当作所有论文、课程、厂商和系统中的唯一标准。如果用户提供了特定来源，仍以来源语境为先。

## 用户请求

> 解释下，什么是 Agent？

## 已验收回答

在当前常见的 AI 工程语境中，**Agent 是一个能够围绕目标，自己判断下一步做什么，并根据执行结果继续调整行动的 AI 系统。**

可以先把它放进这条链路中理解：

> 用户给出目标
> → Agent 判断下一步
> → 调用工具或执行操作
> → 查看返回结果
> → 判断任务是否完成
> → 没完成就继续行动

例如，用户告诉一个合同审查 Agent：

> 检查这份合同有哪些风险，并给出修改建议。

它可能会：

1. 读取合同；
2. 判断需要检查哪些条款；
3. 查询公司制度或法规；
4. 根据查询结果识别风险；
5. 发现材料不足时继续查找或向用户提问；
6. 最后输出审查结果。

这里真正让它成为 Agent 的，不是“会回答问题”，也不只是“调用了工具”，而是它能在任务执行过程中，根据目标和当前结果决定下一步。

### 判断一个系统算不算 Agent，主要看三件事

1. **有没有一个需要完成的目标**

   不只是回答一句话，而是要把一项任务推进到某个结果。

2. **下一步是不是由 AI 在运行过程中判断**

   如果所有步骤都提前写死，它更接近普通工作流。

3. **能不能根据执行结果调整后续行动**

   查到的信息不够，就继续查；操作失败，就换方法；任务完成，就停止。

### 一个容易误判的反例

一个客服机器人收到“查询订单”后，固定调用订单接口，再把结果回复用户。

它虽然使用了大模型、调用了工具，也完成了一个操作，但如果整个过程都是提前写死的，AI 没有判断“下一步做什么”，它更准确地说是一个带大模型的固定工作流，不是典型 Agent。

### 边界情况

Agent 不一定要调用很多工具，也不一定要执行十几个步骤。

即使只有一个工具，只要 AI 能判断什么时候调用、使用什么参数、返回结果是否够用，以及接下来继续、追问还是结束，它仍然可能是 Agent。

所以更实用的判断规则是：

> 不要只看系统有没有大模型、有没有工具；要看任务执行过程中，下一步行动是不是由模型根据目标和当前结果动态决定的。

### 用新案例检验

一个知识库问答系统会自动搜索资料，但无论搜索结果好不好，都只搜索一次，然后直接生成答案。

它算 Agent 吗？关键缺少了上面哪一项能力？

## 评估要点

- 开头直接回答，不要求普通用户先选择“面试、工程还是论文”模式；
- 先给关系链，再提炼判断标准；
- 正例、反例和边界例都解释为什么；
- 不把“使用大模型”或“调用工具”单独当作 Agent 的充分条件；
- 结尾使用未见案例检查判断能力；
- 若用户指定某一课程或框架，放弃本示例的通用语境，改按来源定义回答。
