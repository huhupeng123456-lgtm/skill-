# 真实能力验收规则

## 判定原则

把“掌握”作为需要证据支持的结论。一次成功只能证明当前路径运行过，不能单独证明用户能够独立完成、适应变化或处理故障。

学习过程中不展示固定学习板。根据用户每轮提交的证据在对话内调整提示强度，只在阶段完成或用户询问时汇总判断。

## 六项掌握证据

只有以下六项均通过，才能报告用户已掌握当前定义的技能范围。

| 能力 | 通过条件 | 可接受证据 |
|---|---|---|
| 核心任务完成 | 用户亲手完成目标闭环，结果可打开、运行、读取或复核 | 成果文件、界面状态、命令输出、真实运行结果 |
| 机制解释 | 用户能说明关键输入、输出、配置和状态变化 | 用户复述、参数解释、数据流或操作影响说明 |
| 条件变化 | 更换一个重要输入、参数、环境或业务条件后仍能完成 | 变式任务结果及差异说明 |
| 故障修复 | 用户能根据现象和证据定位并修复至少一个常见故障 | 报错、日志或 Trace，诊断过程，修复后结果 |
| 边界判断 | 用户能说明适用条件、风险、权限和生产差距 | 边界清单、风险说明、需要人工确认的动作 |
| 独立挑战 | 在没有逐步提示和代做的情况下完成同类新任务 | 独立产物及验收证据 |

## 提示与独立性

- **完整提示**：给出明确入口和逐步操作，只用于建立第一条成功路径。
- **部分提示**：只给目标、关键约束或排查方向，用于变式和纠偏。
- **无步骤提示**：只给任务、边界和验收条件，用于独立挑战。

用户在独立挑战中请求或接受了决定性步骤提示，本轮挑战即转回练习，不判定独立完成。可以解释术语、澄清目标和提醒安全边界，但不得透露核心操作顺序或最终配置。

## 证据检查

检查证据时确认：

1. 证据对应当前环境和当前任务，不是无关旧截图或示例结果；
2. 结果证明了目标状态，不只证明按钮被点击或命令被执行；
3. 关键配置、数据、日志或 Trace 可以回溯；
4. 使用 Mock 时已明确标记，未声称为真实客户数据或生产效果；
5. 高风险动作经过隔离、备份、预览或人工确认。

证据不足时，直接指出还缺什么以及如何补充，不用模糊的“基本掌握”“应该会了”。

## 完成与未完成

### 通过

简洁报告：

- 完成的真实成果；
- 六项能力对应的证据；
- 已知边界和生产差距；
- 下一项最小练习。

### 未通过

明确报告：

- 已经通过的部分；
- 未通过的具体能力；
- 暴露该缺口的证据；
- 下一次只需补练的最小任务。

不要因为学习时间较长、用户表达自信或大部分步骤成功而降低门禁。
