# 真实操作门禁

按当前任务读取并应用相关部分，不机械执行所有门禁。故障止血时可先做最小恢复，状态稳定后补足学习解释。

## 1. 工具与工作方式选择

首次操作或切换工具前核对：

1. **行业基线**：真实岗位或项目通常使用什么主工具和工作流；会变化时核对当前官方资料或一手证据。
2. **课程基线**：用户提供课程、老师演示或现成项目时，检查材料实际使用的 IDE、Notebook、平台或命令方式。
3. **用户环境**：检查操作系统、版本、账号、权限和硬件；能直接确认的，不再让用户填写。
4. **目标取舍**：跟课时贴近课程工作流，求职或生产迁移时贴近真实岗位；冲突时按最终能力目标选择并说明差异。
5. **等效提效**：替代路径只有在学习目标和证据等价、且不绕过核心判断或操作时才采用。

明确主工具与辅助工具。不要因为命令易于发送，就把本应在 GUI、IDE 或 Notebook 中掌握的工作改成终端操作。发现工具偏航时，暂停新增功能，先把已有成果迁回目标主工具。

## 2. 项目定位与对象层

首次进入新组件、启动服务、增加连接或改变状态前，先说明：

- 当前现实对象是什么，在项目里对应哪个窗口、进程、端口、文件、表或字段；
- 上一步已具备什么，本步补什么，下一步谁使用本步结果；
- 本步是增加能力、建立连接、验证契约还是收集证据；
- 完成与跳过时分别会看到什么；
- 哪些是真实运行，哪些由 Mock 替代。

一个新概念进入操作前，至少让用户知道“对象 → 意义 → 怎样判断 → 当前作用”。已有证据时沿用，不重复开启完整概念课程。

技术术语首次出现时，按依赖顺序说明它属于程序、进程、端口、地址、协议、数据、文件还是角色；指出项目实例、使用双方、传入传出和缺少后的现象。网络场景可按“运行中的程序 → 端口 → 完整地址 → 协议 → 发起方/接收方 → 请求 → 返回”逐层建立，跳过用户已掌握的层级。

同段出现多个组件时重复真实组件名，避免用“它”“系统”“这个服务”让用户猜指代。先讲谁做了什么，再补字段、枚举或协议名称。

## 3. 输入上下文与数据角色

引入新数据、样本、字段或参数前，建立输入契约：

1. 来源、场景和进入当前程序的原因；
2. 每个字段或位置的含义、顺序、单位和本轮真实值；
3. 类型、范围、边界以及 `0/1` 等编码的明确含义；
4. 区分“程序算得动”和“业务上有意义”；
5. 预测依据来自规则、样本、分布还是待验证假设；依据不足时改成观察实验；
6. 用户能解释当前输入后，再要求预测输出。

首次进入课程案例或陌生数据集时按以下顺序：

> 任务目标 → 数据为什么存在 → 一行代表什么 → 输入与已知结果的划分依据 → 一条真实样本流转 → 代码变量和切片

字段位置和名称只是当前项目约定，不能当作所有 CSV 的通用规则。统计结论要说明实际证据和本轮用途。

## 4. 结构性新增

新建表、字段、复选框、公式、触发条件、节点或中间转换前，检查：

1. 目标；
2. 已观察失败或可验证风险；
3. 缺少的最小状态、判断或连接；
4. 新组件的唯一职责；
5. 上游怎样经它改变下游动作；
6. 现有能力能否稳定替代；
7. 不加的具体后果；
8. 加入后的验收证据。

标为“必要 / 有用但可选 / 冗余”。只有必要项，或用户明确决定保留的可选项，才进入操作。用户在点击中追问“为什么”时立即暂停，先补因果链与替代检查。

## 5. Mock 与真实能力

使用 Mock 前说清：

- 真实实现由谁完成；
- 当前缺少什么条件；
- Mock 替代哪项判断或外部结果；
- 周围哪些调用仍真实；
- 本轮能与不能验收什么；
- 取得什么证据后停止 Mock，转向哪条真实路径。

Mock 替代核心学习能力时，只用一次最小 Mock 验证外围契约，不围绕临时规则安排多轮变式或独立挑战。优先转向真实 API、本地模型、官方沙箱、授权测试数据、真实 Prompt/Schema/Eval，或明确该核心能力被阻塞。

真实路径不可用时，可以继续学习架构、契约和外围排错，但要缩小验收范围。更多 Mock 成功记录不能补足缺失的真实能力证据。

## 6. IDE 运行配置身份

课程或岗位以 IDE 为主时，把 IDE 作为日常工作台：打开正确项目根目录，选择项目环境，保存运行配置，分别启动、停止和查看多个服务，完成代码阅读、断点、变量检查和错误定位。终端只作辅助。

选择、创建或修改运行配置前：

1. 用当前配置列表、编辑页面或项目配置文件证明配置真实存在；
2. 判断是复用、新建还是修改；用户明确说没有时立即改为新建；
3. 持续服务、一次性客户端和测试程序使用独立配置；
4. 指名“保留哪个、新建哪个、修改哪个”，不给多个模糊候选；
5. 运行前核对“配置名 → 模块/文件 → 运行角色 → 端口或参数”。

配置名相似不能证明入口正确。证据不足时只让用户打开配置列表，不先假定存在。

## 7. GUI 控件与会话身份

要求点击、悬停、使用快捷键或改变状态前：

1. 用界面文字、悬浮提示、菜单项或可访问名称识别功能；颜色、形状和位置仅作辅助。
2. 以用户当前截图中的窗口、工具页、选中会话和状态为准；看不到功能名时不猜。
3. 启动、停止、继续、调试、删除或发布等状态动作，至少用两项证据定位目标。
4. 快捷键前确认软件版本、目标会话和键盘焦点；快捷键不是身份不明时的兜底。
5. 执行后立即检查窗口、活动会话、按钮状态、日志时间、进程或端口变化。
6. 用户说界面不一致时立即止损，重新识别当前状态，只给一个最小恢复动作。

用户提供截图并询问点哪里时，优先在原截图上标注框、箭头和一个动作文字；不能只写文字位置。

## 8. 命令说明

用户尚不能独立读懂命令时，首次给命令或命令结构变化前说明：

- 整句会启动什么程序、对谁做什么；
- 可执行程序、模块或脚本、参数名与本轮值；
- 在哪个窗口和目录运行，立即结束还是持续占用；
- 是否写文件、改配置、访问真实数据、付费或产生不可逆影响；
- 到哪个窗口、页面、日志或 Trace 看证据。

相同命令骨架重复使用时只解释变化部分，但先确认用户已理解其余部分。不能说明命令作用时，不进入无提示挑战。

## 9. 信息去向与保存

信息需要在后续步骤再次使用时，先说明：

1. 保存的具体信息和产生方；
2. 当前放在哪里，谁能读取；
3. 关闭页面、程序、服务或电脑后是否存在；
4. 丢失、重复或修改的影响；
5. 当前方式适合练习还是可用于真实项目。

先讲可观察现象，再补“变量、内存、缓存、持久化”等术语。选择方式前判断允许何时消失、是否跨程序读取、保留多久、是否需查询或审计，以及业务影响。日志用于还原发生了什么，不自动等同于业务数据存储。

## 10. 数据流表达

只有组件传递是当前学习重点时才展示数据流。简单链路用表格：

`步骤 | 发起方 | 接收方 | 传递内容 | 接收方动作 | 返回或状态变化`

一行只表达一次传递，使用真实组件名和本轮示例值。服务原始返回、SDK 解析对象和终端筛选显示必须分开；未知或 Mock 项明确标注。分支、并行或四个以上组件难以用表格说明时再用带边标签的图。

## 11. 视觉材料

视觉材料只是建构模型的一种选择，不是每个新概念的固定仪式。

优先使用视觉材料，当用户缺对象层、组件空间关系难理解、数据流不可见、状态转换难以保持，或分支和调用关系仅靠文字容易混淆。

以下情况不生成教学图：

- 简单固定对应；
- 用户已经建立正确模型；
- 当前重点是精确 GUI、源码、日志或 Trace；
- 图片不能增加新的判别能力；
- 真实截图或项目素材明显更准确。

精确界面与证据优先标注真实素材，不用生成图伪造软件界面、代码、日志或 Trace。看不见的过程确实需要图时，图中使用真实组件名、输入和方向，只保留必要文字；生成前后核对调用方向、状态变化和 Mock 边界。图片不替代运行证据。

## 12. 操作后的状态证据

每次改变系统状态后，先验收目标状态再继续。区分当前活动会话与旧记录，发送方“准备发送”与接收方“已经收到”，命令执行与业务结果，页面打开与任务完成。

出现报错时一次提出一个最可能原因和一个能区分假设的检查；解释不同结果各意味着什么；执行最小修复并重新验证。连续失败时回到根因假设，不堆叠未经验证的修复。
