# B 端正式材料交付前审核

## 核心原则

- **只改文字不动排版**：绝不修改字体、字号、行距、颜色等格式属性
- **在对话中直接返回文本**：不生成文件，审核结果以结构化文本输出
- **结论先行**：先给总体判断（可交付 / 需修改后可交付 / 不可交付），再展开细节
- **零容忍编造**：涉及项目信息无法确认时，必须标注「需确认」
- **没有依据的内容不能写**：SOW/合同/会议纪要/客户原始材料里没有的，不能出现在正式文档中

## 前置确认（必须执行）

审核开始前，先向用户确认以下信息。如果用户没有提供，直接询问，不要假设：

1. **文档类型**：验收报告 / 试运行报告 / 项目总结 / 方案书 / SOW / 汇报材料 / 会议纪要 / 其他？
2. **材料来源**：是否有 SOW、合同、会议纪要、客户原始材料可供核对？
3. **文档组成**：是否包含截图 / 表格 / 案例 / 业务数据？（这决定了哪些审核维度适用）
4. **项目阶段**：试运行 / 验收 / 已交付 / 规划中？（这决定了"已实现""试运行"等措辞的审查标准）

确认完成后，根据文档实际情况选择适用的审核维度。如果某维度不适用（如纯文字材料没有截图），在输出中标注"本维度不适用"即可，不要硬审。

## 审核工作流

按用户要求的"三遍审核法"执行：

### 第一遍：查事实

逐条检查内容真实性类问题。核心问题：有没有写错范围、入口、能力、对象？

加载 references/b-end-document-rules.md 中"一、内容真实性类"（规则 1-9），逐项核对。

### 第二遍：查逻辑

检查逻辑一致性类问题。核心问题：背景、建设、效果、价值是否连贯？

加载 references/b-end-document-rules.md 中"二、逻辑一致性类"（规则 10-15），逐项核对。

### 第三遍：查格式与语言

检查格式规范类和语言表达类问题。

加载 references/b-end-document-rules.md 中"四、格式规范类"（规则 20-32）和"五、语言表达类"（规则 33-38），逐项核对。

如果文档包含业务案例和截图，额外检查"三、业务场景匹配类"（规则 16-19）。

## 10 类问题输出格式

审核结果必须按以下 10 类问题输出。每类给出评分（通过 / 需修改 / 严重问题）和具体问题：

```
## 审核结果：XXX（可交付 / 需修改后可交付 / 不可交付）

### 总体评价（1-2句话）

---

### 一、事实依据问题 【评分】

SOW/合同/会议纪要/客户原始材料里没有的内容、编造的事实。

**问题 1**
- 原文：「...」
- 问题：...
- 建议：...

### 二、能力夸大问题 【评分】

实际没实现却写成已实现、未来能力写成当前能力、过度宣传。

**问题 1**
- ...

### 三、范围错误问题 【评分】

知识库、部门、资料、入口、面向对象写错。

**问题 1**
- ...

### 四、场景不匹配问题 【评分】

案例、截图、问题不贴合业务；案例不典型；截图没有业务属性。

（如文档无案例/截图，标注"本维度不适用"）

### 五、模板残留问题 【评分】

从其他材料复制来的不适配内容（部门名、知识库名、入口、截图、业务对象未改）。

### 六、逻辑断裂问题 【评分】

标题与正文不匹配、背景-建设-效果-价值连不上、总述大于正文。

### 七、价值拔高问题 【评分】

业务价值过度宣传、强行拔高、空话套话。

### 八、语言不正式问题 【评分】

口语化、主观推测、责任不清、绝对化表达。

### 九、格式不统一问题 【评分】

缩进、行距、字号、字体、编号、标点、空格、段落间距不统一。

（如用户明确说"不用审格式"，标注"本维度跳过"）

### 十、提交风险判断 【评分】

哪些问题会导致被甲方/老板直接打回。

---

### 全部问题清单（按风险等级排序）

**严重问题（必须修改，否则可能被甲方/老板打回）：**
1. ...
2. ...

**需修改问题（建议修改，影响专业度）：**
1. ...
2. ...
3. ...

**轻微问题（可选优化）：**
1. ...

### 审核依据说明
- 事实核对来源：XXX（SOW / 会议纪要 / 客户材料 / 用户口述）
- 未核对项：XXX（因缺少材料无法确认）
```

## 评分标准

- **通过**：该维度无问题或只有极轻微瑕疵
- **需修改**：有 1-3 处需要修改的问题，不影响整体交付
- **严重问题**：有结构性错误、事实性错误或可能被甲方打回的问题，必须修改后才能交付

## 最终交付判断

| 情况 | 结论 |
|------|------|
| 无"严重问题"维度，且"需修改"≤2个 | **可交付** |
| 无"严重问题"，但"需修改"≥3个 | **需修改后可交付** |
| 任意维度出现"严重问题" | **不可交付** |

## 关键检查口诀

审核时每看到以下句子，必须追问"依据是什么"：

已完成、已实现、已上线、支持、显著提升、自动生成、实时分析、统一入口、多端使用、多语种问答、权限控制、业务价值明显、全面覆盖、全流程、全场景。

回答不出依据 → 改弱或删除。
