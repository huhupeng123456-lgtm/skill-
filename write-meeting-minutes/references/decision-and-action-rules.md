## 一、什么算决策

决策是会议中已经确定、暂时确定、明确否决或必须后续拍板的选择。只要它会影响范围、方案、人员、时间、资源、承诺、验收或后续行动，就要进入候选账本。

不要把“有完整原因”作为决策成立的前提。会议明确拍板但没有解释原因时，仍然记录决策，并把原因写为 `[会议未说明]`。

常见决策信号包括：

- “就按这个做”“先这么定”“最终采用”“统一按……执行”；
- 在多个方案中选择或排除一个方案；
- 调整产品范围、优先级、版本、节点或验收口径；
- 明确由谁负责、何时交付、投入什么资源；
- 领导作出明确指示，且没有被后续发言推翻；
- 多方对某项方案形成明确一致；
- 明确暂停、取消、否决或推迟一项工作；
- 给出带条件的结论。

以下内容不能直接认定为已决策：

- 个人建议、猜测、设想；
- “可以考虑”“要不试试”“我倾向于”等未确认意见；
- 纯信息同步；
- 无人回应或确认的发散观点；
- 与会议目标无关的经验分享。

## 二、决策状态

| 状态 | 判断标准 | 输出位置 |
|---|---|---|
| 已决策 | 已明确拍板或形成一致，后续可直接执行 | 核心结论 / 决策 |
| 有条件决策 | 结论已确定，但成立依赖明确前提 | 核心结论 / 决策，并写清条件 |
| 暂定 | 当前先按某方案推进，后续仍可能调整 | 核心结论 / 决策，并标注“暂定” |
| 待确认 | 结论基本明确，但执行所需事实、口径或行动字段缺失 | 待确认、待对齐的疑问点 |
| 待决策 | 提出了选项或问题，但会议没有形成结论 | 遗留争议、下期待讨论议题 |
| 已否决/撤回 | 明确不采用，且影响范围或后续行动 | 核心结论 / 决策或遗留争议 |
| 信息不足 | 转写或上下文不足，无法判断是否拍板 | 待确认、待对齐的疑问点 |

## 三、决策分类

使用分类检查遗漏，不在最终纪要中机械展示：

1. 范围：做什么、不做什么、版本边界、目标用户和场景。
2. 方案：产品、技术、流程、供应商或实施路线。
3. 优先级：先后顺序、资源倾斜、必须项和后置项。
4. 时间：里程碑、上线、评审和延期。
5. 责任：负责人、配合方、审批人和升级路径。
6. 资源：预算、人员、数据、环境、模型和外部支持。
7. 验收：成功标准、测试范围、客户确认和交付口径。
8. 风险处置：止损、降级、替代方案和风险接受。
9. 沟通：对客户、领导或团队的同步口径。
10. 撤销：取消、暂停、拒绝或替代此前安排。

## 四、决策扫描方法

### 第一轮：按时间顺序收集

逐段标记所有可能影响后续行为的表达。宁可多收候选，不要提前压缩。

### 第二轮：按议题回查

对每个议题回答：

1. 最终决定是什么？
2. 谁确认的？
3. 适用范围和条件是什么？
4. 是否替代了此前结论？
5. 是否有未确认事实或口径？
6. 是否存在仍需讨论的真实分歧？
7. 该结论引出了哪些行动？

### 冲突处理

- 同一事项前后结论不同：采用最后一次明确确认的结论。
- 后续只是个人反对但没有重新拍板：保留原决策；只有异议仍需处理时，才列为遗留争议。
- 无法判断最终确认：不得选边，列为遗留争议。
- 决策分散在多个发言中：合并为一条完整决策，在内部保留多个证据位置。

### 去重原则

只有对象、动作、适用范围、条件和结果均相同时才合并。以下情况不得误合并：

- 同一方案在不同业务范围下的决定；
- 同一任务分给不同责任人；
- 同一节点的初稿、评审和正式交付；
- 暂定结论与后续正式结论。
- 同一发言中分配给不同人员的任务；
- 同一人员承担的不同业务模块或不同交付成果；
- 用户端功能、管理端功能、数据统计和客服配置等可以独立验收的工作。

## 五、待确认与遗留争议的边界

### 待确认、待对齐

用于已经可以继续推进，但存在信息缺口或口径不一致的事项，例如：

- 行动项缺负责人、精确日期或交付成果；
- 数据、范围、术语、接口或验收口径需要确认；
- 已有方向，但生效条件尚未核实。

### 遗留争议、下期待讨论

用于会议尚未形成选择、存在真实分歧或明确后置讨论的事项，例如：

- 多个方案仍未选定；
- 关键干系人意见冲突；
- 需要新增材料或专项会议后才能决定；
- 本次会议明确不讨论、留到下次的议题。

同一事项不要同时出现在两个区块。先判断它缺的是“事实/口径”，还是“最终选择”。

## 六、行动项硬性规范

行动项必须来自明确承诺、明确指派或已决策事项要求的后续动作。

每条行动必须具备三个必填要素：

| 要素 | 硬性要求 |
|---|---|
| 负责人 | 明确到具体人员；不写“相关人员”“项目组”“团队” |
| 截止日期 | 精确到 `YYYY-MM-DD`；不写“尽快”“近期”“后续” |
| 交付成果 | 明确具体产出及版本或会议，例如“AI 优化方案 V1.0”“接口清单”“方案评审会” |

建议同时保留行动要求、优先级和对应决策，但不能用这些字段替代三项必填要素。

时间处理规则：

- 原文给出具体日期：按原文记录。
- 原文给出“下周五”等可唯一换算的日期，且会议日期明确：换算为绝对日期。
- 原文只说“下周”“近期”“尽快”：截止日期写 `[待确认]`，并加入待确认区。
- 不根据项目经验或个人判断补日期。

缺失任一必填要素时：

1. 保留行动，不要漏项；
2. 缺失字段写 `[待确认]`；
3. 在待确认区新增对应问题；
4. 不把该行动描述成已经具备完整执行条件。

正确表达示例：

> 张三于 2026-07-25 输出 AI 优化方案 V1.0，并同步项目群评审。

以下内容不是合格行动项：

- “后续优化一下方案”；
- “大家再关注一下”；
- 纯建议、愿望或已完成工作；
- 没有责任人、日期和成果的模糊提醒。

## 七、重要性与风险

| 级别 | 判断标准 |
|---|---|
| P0 | 影响客户承诺、上线、范围、预算、安全合规、核心路线或不可逆操作 |
| P1 | 影响里程碑、主要责任、跨团队协同、外部依赖或核心交付质量 |
| P2 | 支撑 P0/P1 决策和行动的必要信息 |

重要性由业务影响决定，不由发言长度、语气强度或发言者表达能力决定。

重要项目的风险单独高亮，但必须包括：

- 风险事实；
- 影响对象；
- 触发条件；
- 已有应对措施或待确认事项。

不要用“存在一定风险”“需要持续关注”等空泛表达。

## 八、证据与不确定性

- 内部候选账本优先记录“发言人 + 时间戳”；没有时间戳时记录“发言人 + 原文短句”。
- 正文默认不展示证据列或大段引文，避免干扰领导阅读。
- 用户要求审计、复核或追溯时，再输出证据附录。
- 不要把推断写成事实。
- 原文存在明显转写问题时使用 `[转写待确认]`。
- 决策原因未说明时写 `[会议未说明]`。
- 只有飞书 AI 总结而没有逐字稿时，完整性判断必须降级，并提示可能遗漏。

## 九、完整性检查

- [ ] 每个议题都有已决策、待确认或遗留争议状态。
- [ ] 所有明确拍板、方案选择和否决都已检查。
- [ ] 所有范围、优先级、时间、责任、资源和验收变化都已检查。
- [ ] 所有领导指示和多人确认都已检查。
- [ ] 所有前后冲突都已找到最终状态。
- [ ] 每项行动都有具体负责人、精确日期和明确交付成果。
- [ ] 缺失行动要素全部同步进入待确认区。
- [ ] 待确认与遗留争议没有重复。
- [ ] 没有因缺少原因或行动字段而删除重要事项。
- [ ] 合并重复项时没有丢失范围、条件或例外。
- [ ] 每位说话人的身份依据已记录；无法确认的姓名没有被猜测。
- [ ] 每条明确分工均已独立入账，并与最终总结逐条对齐。
- [ ] 每位被点名承担工作的参会人至少对应一条责任或行动候选。
- [ ] 每项明确要求修改的 PRD、需求表、方案或看板均已记录。
- [ ] 长会议的所有时间窗口都已检查，没有只扫描开头和结尾。

## 十、说话人身份与责任账本

### 身份证据优先级

1. 用户在当前对话中的明确确认；
2. 发言人自报姓名；
3. 其他参会人无歧义点名；
4. 参会人名单与上下文唯一对应；
5. 无法确认时保留说话人编号。

用户的明确纠正覆盖转写文本中的错名或模糊称呼。身份映射一旦确认，责任账本、行动项、审校结果和最终纪要必须使用同一姓名。

### 责任分配信号

以下表达全部进入责任候选，不因缺少日期或交付物而删除：

- “你负责……”“这个给你”“这个模块分给 XX”；
- “你跟 XX 做……”“我们两个一起做……”；
- “XX 做用户端，YY 做管理端”；
- “做完这个再支援……”“先把数据库/文档做完”；
- 会议末尾对人员和模块的汇总、重申或调整。

内部责任账本至少记录：

| 字段 | 要求 |
|---|---|
| 责任人 | 使用已确认姓名；不确定时保留说话人编号 |
| 协作人 | 原文明确时记录，不把协作人降为普通参会人 |
| 工作对象 | 写到可独立验收的模块或事项 |
| 动作 | 设计、开发、修改、评审、确认、同步等 |
| 交付物 | 原文没有时标 `[待确认]` |
| 截止日期 | 原文没有时标 `[待确认]` |
| 证据 | 发言人、时间戳和原文短句 |
| 最终状态 | 已确认、暂定、撤回、被后续分工替代或待确认 |

同一段话出现多个模块时逐项建账，再决定最终纪要是否合并展示。不得把“控制台”笼统替代原文明确列出的“数据统计”和“客服”等独立模块。

## 十一、长会议覆盖检查

会议超过 30 分钟或 10,000 字时，建立 10 分钟时间窗覆盖表：

| 时间窗 | 已检查 | 身份候选 | 决策候选 | 分工候选 | 文档变更 | 风险/待确认 |
|---|---|---|---|---|---|---|
| 00:00–09:59 | 是/否 | 数量 | 数量 | 数量 | 数量 | 数量 |

检查顺序：

1. 按时间窗逐段扫描，不允许跳过“闲聊较多”的区间。
2. 单独复查最后 20% 的逐字稿，优先查找总结、撤回、分工和下周安排。
3. 按说话人反查：每位发言人的承诺、被指派事项和身份线索是否有记录。
4. 按对象反查：每个产品模块、技术模块和下游文档是否有最终状态。
5. 将所有分工候选与行动项、PRD 变更和最终纪要逐条对账。

时间窗口只是覆盖证明，不是最终章节。正式纪要仍按四段式输出。
